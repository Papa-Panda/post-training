# 01 — Queueing, latency, and token accounting

## 1. Request timeline

For request $i$, record arrival $a_i$, first admission $s_i$, first token $f_i$, final token $c_i$, prompt length $P_i$, and generated length $G_i$.

- Queue delay: $Q_i = s_i-a_i$.
- Time to first token: $TTFT_i = f_i-a_i$. This includes queueing, scheduling, and prefill.
- Inter-token latency (ITL): every gap between adjacent output tokens. Do not infer its tail from a single average.
- Mean time per output token (TPOT), when $G_i>1$: $$TPOT_i = \frac{c_i-f_i}{G_i-1}$$
- End-to-end latency: $$E2E_i = c_i-a_i$$

The approximation $E2E \approx TTFT+(G-1)TPOT$ is useful only when `TTFT` and `TPOT` come from the same request population. Always publish percentiles with the workload distribution.

## 2. Queue stability

Let $\lambda$ be the offered request rate and $\mu$ the sustainable completion rate for the exact workload. The utilization shorthand is $\rho=\lambda/\mu$. When sustained $\rho\ge 1$, backlog grows until admission control, timeout, or failure intervenes. Even below one, burstiness and heavy-tailed output lengths can dominate P95/P99.

For a stable measured window, Little's law relates average number in the system $L$, effective throughput $\lambda_{eff}$, and average end-to-end time $W$: $$L = \lambda_{eff} W$$

Use **completed** request throughput for $\lambda_{eff}$. Plugging offered load into Little's law during overload is a common error because arrivals and completions differ.

A rollout engine is a two-phase server:

- Prefill work offered: $$D_{pre} = \lambda E[P]$$
- Decode work offered: $$D_{dec} = \lambda E[G]$$

Compare each with its measured phase capacity. One aggregate tokens/s number hides whether prompt ingestion or decode is the bottleneck.

## 3. Token ledger

Maintain monotonically reconcilable counters:

| Counter | Meaning |
|---|---|
| `prompt_tokens_requested` | Prompt tokens presented by clients |
| `prompt_tokens_processed` | Actual prefill work, including recomputation |
| `prompt_tokens_cached` | Prompt tokens reused from a compatible prefix cache |
| `generation_tokens_attempted` | Every output token generated, including later-dropped work |
| `generation_tokens_completed` | Output tokens belonging to completed trajectories |
| `generation_tokens_accepted` | Completed output tokens admitted to the learner dataset |
| `generation_tokens_retried` | Work generated by explicit retries; keep separate from recomputed prefill |

The accounting identities should hold over a closed run:

$$generation\_tokens\_accepted \le generation\_tokens\_completed \le generation\_tokens\_attempted$$

$$wasted\_generation = generation\_tokens\_attempted-generation\_tokens\_accepted$$

Throughput measures executed work; useful goodput measures accepted work:

$$throughput = \frac{generation\_tokens\_completed}{wall\ time}$$

$$useful\ goodput = \frac{generation\_tokens\_accepted}{wall\ time}$$

For group sampling with $n$ candidates per prompt, track prompt groups as well as sequences. Request throughput can rise while completed groups fall if stragglers delay group closure.

## 4. Cost without invented prices

Given measured accelerator-hours $H$, a user-supplied rate $C$, and $N_{accepted}$ accepted trajectories:

$$cost\ per\ accepted\ trajectory = \frac{HC}{N_{accepted}}$$

Also report cost per accepted output token. Do not use P95 latency as a substitute for total accelerator-hours, and do not embed a cloud price without its source, date, region, commitment model, and hardware configuration.

## 5. Percentiles and censoring

A timed-out request is not an ordinary slow completion. Report:

- completion-latency percentiles among completed requests;
- timeout rate and timeout threshold;
- unfinished/censored requests at measurement end;
- queue depth and oldest-request age;
- separate warm-up and steady-state intervals.

The CPU lab exposes these categories rather than silently dropping unfinished work.
