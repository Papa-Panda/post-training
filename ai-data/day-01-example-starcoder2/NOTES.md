> 更正第一轮索引中的一句话：**“600+”指最终覆盖 619 种编程语言，不是 600+ 条过滤规则。** 论文公开的是一组分层 basic / language-specific / source-specific gates，以及去重、PII、防污染、恶意代码和 opt-out 流程。

## 第二轮复习（2026-09-01）

### 1. 核心命题

这篇真正解决的不是“多抓一些 GitHub 代码”，而是：**怎样把规模巨大、权属不一、重复严重、质量异质且可能泄漏 benchmark 的开源代码，变成可追溯、可删除、可审计、可按模型容量配比的训练资产。**

关键对象不是单一 quality score，而是带 provenance 的数据记录：

$$z=(\text{repo},\text{commit},\text{path},\text{language},\text{license},\text{content},\text{source})$$

策展过程可写成一串门禁：

$$D_{train}=G_{mix}\circ G_{optout}\circ G_{risk}\circ G_{contam}\circ G_{dedup}\circ G_{quality}\circ G_{license}(D_{raw})$$

每个 $G$ 都回答不同问题：能否合法/负责地用、是否像代码、是否重复、是否泄漏评测、是否含隐私或恶意内容、最终是否与模型容量和目标分布匹配。论文的核心贡献是把这些约束组织成端到端工程系统，而不是证明某一条 heuristic 普适最优。

### 2. 图谱位置

- **前驱**：The Stack v1 / StarCoder / SantaCoder 提供开放代码语料、opt-out 与 MinHash-LSH 去重基础；StarCoder2 将源扩到 Software Heritage，并增加更完整的 license、PII、decontamination、malware 与多源数据处理。
- **后继**：Day 14 对同一工作做完整 code-pretraining 复盘；Day 24 D4 / SemDeDup 把“去重”推进到语义近重复与覆盖保持；Day 25 FineWeb 强调逐级消融与可复现过滤归因；Day 27 OSS-Instruct 在干净代码上构造 instruction data；Day 30 将 train–eval 隔离推进到 surface + semantic contamination gate。
- **直接对比 Day 24 D4**：StarCoder2 用 5-gram MinHash + LSH、Jaccard 0.7 做可扩展的 near-dedup，并按 stars / forks / 最新 commit 选簇代表；D4 更关心 embedding 空间里的语义重复和 prototype-based diversification。前者便宜、可解释、适合数亿文件粗筛，后者更能发现改名/改写后的语义冗余并显式保覆盖。两者是 **cascade 互补**，不是替代关系。
- **与 Day 30 的边界**：训练集内部去重优化的是 token 效率与分布；benchmark decontamination 保护的是评测可信度。StarCoder2 的空白归一化字符串匹配召回有限，Day 30 的语义级匹配应成为后置的定向质量门。

### 3. 机制深挖

#### 3.1 来源、权属与可追溯性

1. 从 Software Heritage `2023-09-06` 图快照中抽 GitHub repo，只保留 main/default branch 的最新 revision；用目录内容哈希去重 repo，目录遍历深度最多 64，压缩后大于 10MB 的文件不取。
2. 许可证先取 GHArchive repo-level 元数据；缺失时用 ScanCode 在 license-like 文件中做 file-level 检测，再沿目录传播 SPDX license。论文只保留 permissive 或 unlicensed，排除 commercial 与 copyleft。
3. 发布 SWHID，使“这条代码来自哪个归档对象”可以追踪；opt-out 可沿 provenance 删除，而不是训练前得到一个无法回溯的文本 blob。

这里最值得迁移的机制不是某个 license 白名单，而是 **lineage first**：先保存来源和版本，再谈后续评分，否则删除请求、污染回溯和错误分析都无法闭环。

#### 3.2 粗质量门：规则不是“600+ 条”

- `go-enry` 先识别 658 种语言；社区对约 1,000 个扩展名做可视检查，排除 130 个扩展名和 39 种语言，最终留下 619 种语言。
- 通用过滤包括：文件超过 100k 行；多数语言平均行长超过 100 或最大行长超过 1,000；`go-enry`/文件头判定 autogenerated；字母占比低于 25%；长 Base64/hex/Unicode 编码块超过阈值。
- 语言特定规则避免一刀切：HTML 要有至少 100 个可见字符且可见文本占比至少 20%；JSON/YAML/Text 等限制行数；assembly/WebAssembly 改用 alphanumeric 比例。

这些 signal 估计的是“像不像可学习的人类代码”，不是“对目标任务有没有边际价值”。因此它们适合高召回 coarse filter，不应直接充当最终 selection score。

#### 3.3 去重、代表样本选择与覆盖

对 code、PR、notebook、issue、documentation 计算 5-gram MinHash，再以 LSH 近似分桶；Jaccard 相似度阈值为 0.7，每个重复簇只留一个样本。若多个候选等价，优先 stars / forks 更多的 repo，再用较新 commit 打破平局。

可把该决策写成：

$$k^*=\arg\max_{z\in C}\big(\alpha\log(1+\text{stars})+\beta\log(1+\text{forks})+\gamma\,\text{recency}\big),$$

其中 $C$ 是 LSH 候选簇。论文实际是规则式优先级，不是学习出的线性分数；上式只是把隐含偏好显式化，便于审计。它保留“更流行/更新”的副本，但不保证保留的是最正确、最完整或许可证最清晰的版本。

#### 3.4 风险门与评测门

- StarPII 对 code / PR / issue / StackOverflow 隐去姓名、邮箱、key、password、IP、username；不同来源采用不同实体子集。
- Benchmark decontamination 删除含 HumanEval / MBPP docstring 或 solution、APPS docstring、GSM8K question、DS1000 prompt 的文件；匹配前去掉空白以提高召回。
- ClamAV + SaneSecurity 扫恶意代码，删除 59,442 / 654M 文件（0.009%）。
- 截止日期后执行 opt-out，删除 91 个用户/组织关联的 1,561 个 repo、22,066 个 source files。

这说明 **低命中率不等于可以省略**：malware 占比很小，但失败成本不对称；decontamination 也不能用总体删除比例评价，而要看是否保护关键 benchmark。

#### 3.5 配比也是 curation

3B/7B 只使用 17 种主流编程语言的 `smol` code subset；15B 才使用 619 种语言的 `full` subset。数据侧的假设是模型容量有限时，过宽的语言覆盖会发生 capacity competition。论文还将 Java 与 JavaScript 下采样到各 200GB、HTML 到 100GB、JSON/XML/YAML 到 8GB，并保留更多 Markdown 作为文档信号。

因此“619 种语言”不是无条件越多越好；它是受模型容量约束的 coverage budget。最终 unique-token pool 分别约为 622B（3B）、659B（7B）、913B（15B），模型通过多轮采样训练到 3.3–4.3T tokens。

### 4. 边界与反例

1. **Popularity bias**：stars/forks 高会系统性偏向热门框架、英文生态和成熟 repo；一个零星但正确的 Rust/内部 DSL 实现可能被热门但陈旧的副本替代。
2. **Recency 不等于质量**：最新 commit 可能正处于迁移中、含 regression 或自动生成产物；“更新”只适合作为 tie-breaker。
3. **词法 near-dedup 会两头出错**：模板代码可能因公共 boilerplate 被误删；变量重命名、函数拆分或等价算法又可能绕过 5-gram Jaccard 0.7。Day 24 的语义去重和 Day 30 的定向 semantic contamination 可补，但也会带来更多误杀。
4. **规则会伤长尾**：低字母比例、长行、encoded-block 等规则可能误杀 assembly、shader、generated-but-useful bindings、压缩模型定义；论文靠语言例外缓解，却不能穷尽 DSL。
5. **最新主干快照丢历史**：只取 latest main revision 很适合静态 pretraining，却丢掉 bug→patch、review→revision 的演化信号；PR/issue 作为独立源只能部分补回。
6. **权属不等于质量**：permissive / unlicensed 是治理分类，不是 correctness score；尤其 unlicensed 数据仍留下法务与使用政策问题。
7. **论文没有证明的事**：模型提升同时混入了数据规模、来源、模型大小、训练 token、上下文长度与 formatting 变化；没有逐门禁、同预算的完整 ablation，所以不能把最终性能归因于某一条 filter，更不能从结果推出“规则过滤一定优于 model-aware selection”。

### 5. 迁移到 coding / post-training data

对一个 500k 条 coding SFT / verifiable-RL 候选池，可落地成下面的 versioned gate DAG；**不直接照搬预训练阈值**，先以 quarantine + audit 校准：

1. `G0 provenance`：保存 source repo、commit time、path、license、generator/checker version；无法追溯的样本先隔离。
2. `G1 coarse quality`：syntax/parser、文件/答案长度、autogenerated/encoded/secret/PII 检测；按语言设例外，不跨语言共用单阈值。
3. `G2 redundancy`：先 exact hash，再对 prompt、solution、test 分字段做 MinHash；重复簇保留“测试最完整、依赖可复现、来源最清晰”的样本，而不是默认保留 stars 最大者。
4. `G3 contamination`：对 HumanEval/MBPP/LiveCodeBench/SWE-bench 建 versioned registry；先 whitespace/token match，再 AST/embedding 候选召回，人工复核高风险簇。
5. `G4 execution`：在沙箱中重跑 unit tests，记录 pass/fail、flakiness、runtime、依赖可安装性；可验证 RL 只接收 verifier 稳定的样本。
6. `G5 coverage`：按 language × task type × difficulty × repo lineage 设最小覆盖；在每个桶内再做质量/难度 selection，避免全局分数吞掉长尾。

最小可执行实验：随机保留 5% audit set；比较 `raw → G1 → G1+G2 → G1+G2+G3+G4` 四个版本，在固定 token budget / seed 下报告 clean benchmark pass@1、contamination hit rate、execution pass rate、unique-repo coverage、长尾语言 delta 与每级保留率。这样才能回答“哪个 gate 真正贡献了收益”，而不只是展示数据越来越少。

### 6. 今天的一道思考题

综合 **Day 01 StarCoder2、Day 24 D4、Day 30 code decontamination**：假设 500k 条 coding SFT 候选中，30% 是词法近重复，5% 与评测集存在语义近邻，Rust/SQL 等长尾合计不足 1%，且执行验证成本只能覆盖 20%。请设计一个两阶段 cascade：

- 先说明 exact/MinHash、semantic dedup、benchmark decontamination、coverage constraint、execution sampling 的顺序与各自优化目标；
- 再说明重复簇中保留哪个样本，如何防止“热门 repo 优先”吞掉长尾；
- 最后给出一个固定 token-budget 的对照实验，区分“真实泛化提升”与“污染/题目变容易造成的虚假提升”。

答案不能只列过滤器；必须说明每一级的误杀对象、复核抽样和可推翻该设计的证据。
