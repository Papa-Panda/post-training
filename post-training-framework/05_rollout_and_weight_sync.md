# 05 — Rollout Engines and Weight Synchronization

## 1. The rollout boundary

vLLM and SGLang are inference/serving engines. A post-training framework must wrap an engine with training semantics:

```text
trajectory request
  = prompt + group + seed + sampling config + required policy version

trajectory response
  = tokens/actions + masks + behavior logprobs + termination
    + loaded policy/tokenizer/decoder versions + engine diagnostics
```

The engine accelerates token generation; the framework owns which requests are valid, how trajectories join environments and rewards, and when generated data may train the policy.

## 2. Publication protocol

A safe full-weight publication has explicit phases:

1. learner commits checkpoint $k$ and immutable manifest;
2. publisher converts or reshards it into inference layout;
3. receiving workers stage all shards;
4. each worker validates shapes, digests, tokenizer/adapter identity, and backend compatibility;
5. workers switch atomically at a request boundary;
6. acknowledgements make publication version $k$ schedulable;
7. old versions drain or are retired according to policy.

Do not label a request with $k$ merely because synchronization started. The behavior version is what the worker had fully loaded when sampling began.

## 3. Full, delta, and adapter synchronization

Let inference weights be $W_b$ and new learner weights $W_k$ .

### Full publication

Transfer $W_k$ . It is simple and self-contained but moves all parameter bytes.

### Delta publication

Transfer

$$\Delta W_{k,b}=W_k-W_b.$$

It saves bandwidth when encoded efficiently, but only if the receiver proves that its base is exactly $b$ . Deltas need sequence/order, integrity checks, and rollback. Floating-point application order can also matter.

### Adapter publication

If training updates only LoRA/adapters, publish the adapter plus immutable base-model identity. This reduces bytes, but the inference engine must apply exactly the same composition/scaling as the learner.

## 4. Log-probability consistency

Recomputing behavior log-probabilities under a training backend can disagree with those emitted by the rollout backend because of:

- different model weights or adapter application;
- tokenizer/chat-template differences;
- truncation, stop tokens, or mask construction;
- precision and kernel numerical differences;
- sampling transformations versus raw model logits;
- sequence packing or position IDs;
- MoE routing differences.

The framework should run a fixed calibration batch and compare token-level deltas:

$$\delta_t=\ell_t^{\rm rollout}-\ell_t^{\rm recompute}.$$

Track median, high quantiles, maximum finite error, and mismatch rate by token position/model version. A tolerance is implementation-specific; it must be established empirically, not copied as a universal constant.

## 5. KV-cache correctness

A KV cache entry is not identified only by token prefix. Its validity depends on a cache identity such as

$$c=(\text{weight digest},\text{adapter},\text{tokenizer},\text{position scheme},\text{attention config},\text{precision},\text{prefix}).$$

After a policy update, cached keys/values produced by old weights generally cannot be reused as if generated by new weights. Safe options are:

- drain old-version requests and discard their caches;
- namespace cache entries by full identity;
- preserve old workers/caches only for jobs that remain explicitly on old policy;
- reuse only framework/backend mechanisms with a proven compatibility contract.

Prefix caching across requests is a serving optimization, not permission to cross policy versions.

## 6. Partial and resumed rollouts

For long agent trajectories, interruption can improve scheduling but changes semantics. A checkpoint for resume needs:

- full token/action prefix and masks;
- environment snapshot or replayable event log;
- behavior policy and cache identity;
- RNG state and decoding configuration;
- tool idempotency/side-effect state;
- declared terminal versus truncated status.

If resume uses the same behavior version, it can be modeled as pausing generation. If resume uses a new version, segments need separate provenance and the learner must support piecewise behavior policies. Concatenating them under the newest version is invalid.

## 7. Context management

Agent rollouts may exceed context limits. A context manager can truncate, summarize, retrieve, or compress history. This changes the state seen by the policy and therefore belongs to behavior provenance.

A context transform $C_h$ yields

$$s_t^{\rm model}=C_h(\text{event history}_{0:t}).$$

Changing $h$ can change action probabilities without changing weights. Store its version/digest, plus enough evidence to replay the model-visible context. [`harness-engineering/`](../harness-engineering/README.md) owns the deeper runtime design.

## 8. MoE routing and route replay

For a mixture-of-experts model, routing decisions can differ between rollout and learner recomputation because logits, precision, batching, or load balancing differ. Then the learner may evaluate a token through different experts than generation used.

An expert-communication backend such as DeepEP can optimize dispatch/combine traffic, but that is separate from the semantic question of whether learner recomputation follows the route taken during rollout.

Possible controls include:

- store routing metadata for selected tokens;
- replay routes when the training backend supports it;
- measure route disagreement on calibration batches;
- ensure auxiliary/load-balancing losses use declared semantics;
- treat route metadata volume as part of the trajectory cost.

Route replay is not automatically correct for every objective: forcing old routes under changed weights may stabilize consistency while deviating from the current model's natural routing. State the estimator and validate held-out behavior.

## 9. Precision is part of the contract

FP8 or other lower-precision training, weight transfer, and inference can reduce memory/communication or increase throughput, but each boundary must name the representation:

- master/training parameter dtype and scaling state;
- published checkpoint or delta dtype;
- inference weight/KV-cache dtype;
- logit and log-probability accumulation dtype;
- quantization/dequantization version and calibration state.

A rollout generated from quantized inference weights is sampled from that deployed policy, not an idealized higher-precision checkpoint. If the learner recomputes log-probabilities under a different numerical policy, measure the resulting ratio mismatch on the calibration corpus. Lower precision is promotable only with finite-value checks, cross-backend agreement, and held-out quality—not a memory saving alone.

## 10. Backpressure and cancellation

Rollout scheduling should propagate learner/buffer pressure:

- stop admitting low-priority prompts above a queue high watermark;
- cancel only at declared safe points;
- distinguish cancellation from policy termination;
- preserve completed evidence before cancellation;
- account for wasted prefill/decode/tool work;
- prevent canceled members from silently changing group statistics.

For tool environments, cancellation must reconcile outstanding side effects and release leases/resources.

## 11. Verification checklist

Before trusting a rollout/training integration:

1. generate a fixed prompt/seed batch under a frozen policy;
2. verify loaded artifact and tokenizer digests;
3. reconstruct learner-visible prefixes and masks;
4. compare rollout and recomputed log-probabilities;
5. test stop/truncation and tool-message boundaries;
6. update/publish once and prove old caches are not mislabeled;
7. crash a publisher midway and confirm the old version remains schedulable;
8. test mixed old/new workers and verify each trajectory records the loaded version;
9. test long-tail cancellation and group disposition;
10. monitor useful accepted tokens, not only engine token rate.

For serving-specific TTFT/TPOT, batching, stress testing, and failure taxonomy, continue in [`vllm-rollout/`](../vllm-rollout/README.md).
