2一句话总结

林浩系统介绍了 RLinf 的设计：用 M2Flow（宏观→微观流转换）把「怎么写工作流」与「怎么调度执行」解耦，靠 Worker / WorkerGroup + DataChannel 三件套抽象、弹性流水线与自动上下文切换两大机制、以及基于性能分析的子图调度，让同一套代码能在 GPU / NPU / 机械臂混布的集群上跑具身与 reasoning 两类 RL，字幕口径下训练吞吐为现有 SOTA 系统的 1.1×–2.13× 。

背景：具身 RL 的负载为什么和 LLM RL 不一样

讲者先立论：具身智能是通往 AGI 的核心路径之一，但它的数据瓶颈最重——真机采集贵（一台机械臂数十万元量级，字幕口径），可扩展的仿真数据是关键路径。他引用 Physical Intelligence 创始人在今年 7 月会议上的判断：面向具身的大规模 RL 训练框架目前仍是空白，RLinf 就是来填这个空的。

具身 RL 的系统难点不在模型，而在负载异构：

  1. 环境是 GPU 渲染/物理模拟，不是张量计算。模拟器吃渲染与显存而非算力，单卡上堆多个模拟器时耗时不随数量线性增长，与 LLM 训练的计算画像完全不同。
  2. 真机是独立硬件。机械臂控制器跑实时内核、与 GPU 驱动不兼容，推理要贴近机器人满足实时性，训练可能在云端大显存机器上，两者天然跨机。
  3. 算法流程分叉大。reasoning 侧是 generation → inference → training 的迭代环；具身/agentic 侧多出模拟器或工具服务（如 search server、MCP 云服务），且 PPO 一类算法还要 reference / reward / critic 多模型并存，各自可能都要训练。

现存系统的两种典型形态都有病：共享式（组件共置同卡）省资源但长尾生成时利用率低、上下文切换开销大；分离式（如 AReaL、AsyncFlow 一类异步流水）缓解长尾但吃硬件、没有异步算法配合时闲置严重。讲者的结论是：没有万金油排布，系统必须把排布本身变成可搜索的自由度。

设计理念：灵活性即效率

RLinf 的核心命题是把灵活性当作效率的来源：执行模式越不固定，调度与优化空间越大，越能适配未来新场景/新算法/新负载。反面的顾虑是灵活性带来复杂性、用户配错反而更慢——解法是让用户只写宏观工作流，复杂性由系统在编译期与运行期吸收。

M2Flow：宏观工作流 → 微观执行流

编程模型叫 M2Flow（Macro-to-Micro Flow Transformation，字幕作「m to flow」）。用户写的是宏观流：组件之间数据怎么走。系统像编译器一样，在执行前与执行中把宏观流分解、重组为优化后的微观执行流。讲者展示的 reasoning RL 工作流（GRPO 风格）在 RLinf 里是一个约七行的函数：数据进 DataChannel → rollout 组件生成 → inference 组件算 log-prob → actor 训练组件更新 → 权重回写，循环往复；具身 online RL 是模拟器与 rollout 组件多轮交互产数据、再统一交给 actor 训练，代码同样不超过十行。

三个核心抽象：

  1. Worker：一个 RL 组件就是一個 Worker 子类，核心逻辑写在一个函数里；Worker 只对接 input/output channel，不需要知道上下游是谁，天然异步。
  2. WorkerGroup：create_group + launch 按 placement 策略在一组进程上启动同一 Worker；组句柄继承 Worker 的全部公共方法，一次调用等价于在所有进程上以 SPMD 方式调用同一函数，调用本身异步、返回句柄，用 wait 语义同步并取回返回值。
  3. DataChannel：组件间的数据通道，带负载均衡语义，多个消费者之间保持公平服务。

Placement 是这套抽象的关键自由度：任意 Worker 可以部署在集群任意节点的任意硬件上——GPU、NPU、机械臂都是一等硬件资源，在 YAML config 里改一两行即可。讲者提到已与华为合作在昇腾 NPU 上跑通 reasoning RL；未来场景完全可以 NPU 做推理、GPU 做渲染、纯 CPU 跑 robot control。

两大机制 + 一个调度器

  1. 弹性流水线：通过调节组件间传递的数据粒度来调节流水线粒度——上游攒满整个 batch 再发就没有流水，上游每做完一个 global-batch 的子块就下发，下游立刻开工、上游同时做下一块，粒度越细流水越深。取舍要同时看性能（加速器利用率、流水气泡）与算法语义（基于 batch 的归一化要求拿到完整 batch），这些约束由调度器统一处理。
  2. 自动上下文切换：核心是分布式硬件锁。Worker 拿到锁时自动 load 模型与显存资源、释放时 offload；锁与 channel 里的数据流信息配合做优先级管理，避免死锁与无谓的反复 load/unload。这实现的是加速器的时间分片复用；空间上不同 Worker 分布在不同硬件，两种维度混合即任意时空调度组合。
  3. 基于性能分析的调度：把整体工作流图切成子图，逐子图求最优：调度器基于各硬件上的性能建模比较时间/空间两种调度方案，组合各子图最优解得到全局执行方案。Q&A 中讲者补充说明：组件间策略构建是「近似穷举 + 剪枝」，显存等硬约束会先剪掉不可行分支，并非全空间暴力搜索。

底层通信是自适应通信层：同机零拷贝 IPC、跨机走加速器 CCL，另提供任意 Worker 间的 send/receive 原语——写明 group 名与组内 rank 即可，不需要像 torch.distributed 那样手动建/毁 process group，连接管理全自动。

后端与异构支持

  • 训练/推理组合两套支持较好：Megatron + SGLang/vLLM，以及 FSDP + HuggingFace（字幕口径）。
  • 基于 Megatron 的动态 batching 已在 reasoning 侧落地（不是规划中功能）。
  • 异构硬件：GPU、昇腾 NPU、机械臂统一 placement；最小调度粒度是单张卡，多个进程也可共享一张卡，即粒度可以细到亚卡级、由用户自定义。
  • 真机：支持多台真机并行 RL（近期合入）。配置方式是在 YAML 里定义 node group（子集群），把每台机器人的 IP、相机等信息登记为 hardware 字段，再把 environment worker placement 到这些节点上；真机与 GPU 在系统眼里是同等级硬件资源，扩展方式一致。

性能与实测口径

讲者给出与现有 SOTA RL 系统的对比：不同集群规模、reasoning 与具身模型上，RLinf 整体训练吞吐高出 1.1×–2.13× ；用 RLinf 训练的模型在相应数据集上达到 SOTA（均为字幕口径，讲者未逐项念出基线名与数据集名）。合作团队在 RLinf 上做的 VLA / π 类模型的 RL 训练也达到 SOTA 效果，算法细节留待后续专场。

Q&A 精华

  • 模型服务与训练服务部署：推理组件就是 RLinf 内的一个组件，可同机、可跨机、甚至云端训练 + 端侧推理；仿真训练主要吃 GPU，真机训练另需机械臂资源。
  • π 类模型显存与时长：A100/H100 均测过；显存推荐 80GB ，40GB 也能跑，需调低 environment 数量与训练 micro-batch ；π 模型收敛时长讲者凭印象答「几天量级」（字幕口径，未给确数）。
  • worker 并行不用 Ray 怎么实现：进程 launch 到节点这一步用 Ray 的 node-level placement，但通信、组件管理、硬件/资源管理都是 RLinf 自研调度层，不依赖 Ray 的 placement group。
  • 模拟器与推理 worker 配比：讲者经验值是 LIBERO 场景下模拟器 : 推理 worker 约 2 : 1 比较好（字幕口径）；具身侧自动配比还在开发中。reasoning 侧已有弹性伸缩解决配比问题：rollout 进入长尾阶段时下调 rollout worker 数、扩 training 侧，不必一开始就把配比调准。
  • FSDP 能否弹性伸缩：理论上可以，团队未实测，目前主要支持 Megatron 侧；FSDP 下每卡训练前 gather 完整模型（取决于 sharding strategy），八卡训练会在每卡加载分片后 gather。
  • GPU 利用率低怎么办：显存允许时调大 batch size 或 environment 数量；rollout 慢通常时间花在模拟器一侧，先把 env 数量拉上去。π0.5 微调支持尚未正式上线，RL 过程中利用率低适用同一思路。
  • 自定义算法/环境改哪里：环境定义在 environment/ 目录、算法在 algorithms/ 目录，文档有专章；八卡卡编译、四卡正常一例讲者未遇过，建议查是否有其他任务共用后四卡或调整 placement 到后四卡验证。

5可迁移

  • 「灵活性即效率」对 RL infra 选型的直接含义：评估一个框架时，先看它把 placement / 粒度 / 共置与否做成了可搜索自由度还是写死模式——前者在负载画像变化（长尾变重、模拟器变多）时不用改用户代码就能重排，这是 RLinf 相对固定执行模式框架的结构性优势。
  • Worker 只对接 channel、不认识上下游，是把「算法逻辑」与「部署拓扑」解耦的最小接口；自己写多组件训练脚本时可借用这个纪律：组件签名里不出现拓扑信息，拓扑集中在一份 placement 配置里。
  • 配比经验可先抄：具身任务先按模拟器 : 推理 ≈ 2 : 1 起步，rollout 慢先加 env 数量而不是先动模型侧；reasoning 侧则把弹性伸缩（长尾时缩 rollout、扩 training）当默认能力索取。
