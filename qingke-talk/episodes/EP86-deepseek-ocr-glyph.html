2一句话总结

本期讲清了一条新路线：文本 token 是稀疏、低信息密度的表示，而把长文本渲染成图片再喂给视觉语言模型，可以在近无损的前提下把输入长度压缩数倍。DeepSeek-OCR 先验证了「压缩后的图像表示能高保真恢复原文」这一可恢复性；Glyph 则进一步把这条路线做成长上下文建模框架——持续预训练让模型学会读渲染文本、用 LLM 遗传搜索自动找最优渲染配置、再做 SFT 与 GRPO，在约 3–4 倍压缩比下达到与领先纯文本长上下文模型接近的性能，并带来实际的推理与训练加速。

问题：长上下文的成本困局与四类现有解法

讲者先给出需求侧的量级：deep research 类系统普遍需要 128K 以上的上下文，coding agent 甚至需要 200K 以上。但上下文越长，训练与部署开销越高，首 token 时间也随之拉长。现有四类主流方法各有短板：

  1. 位置编码外推（如长度外推类方法）：32K 训练的模型可外推到 128K 推理，省的是训练开销，推理时仍要按 128K 长度全额计算，注意力仍按 $O(n^2)$ 扩展，且外推越长精度下降越明显。
  2. 稀疏/线性注意力：输入 token 数本身不变，长度到 128K 甚至 1M 以上仍会出问题；讲者还引 MiniMax 的工作指出线性注意力可能反伤推理能力。
  3. RAG 类方法：大幅缩减输入 token 的代价是信息损失（如把 128K context 砍进 32K 模型），agent 式记忆管理还会因多轮反复推理引入显著延迟。

由此引出本场的核心问题：能否找到一种表示，把输入上下文尽量无损地压缩——保留信息的同时明显缩短输入长度。一个来自 API 使用的直观观察支撑了这个方向：同一段长文字，纯文本输入要 400 多个 token，排版截图输入只要 67 个 token，约 6 倍压缩比；而现在的视觉语言模型已经能很好地读出这种压缩图片里的内容。

DeepSeek-OCR：先验证「可恢复性」

讲者对 DeepSeek-OCR 的定位是理论验证：无损建模的前提是能从压缩后的表示里把原文恢复出来。它的架构关键在下采样位置——把大幅下采样前置，达到 16 倍压缩，而通用视觉语言模型通常只有 2×2、即约 4 倍；激进压缩之所以可行，是因为它专做 OCR 类任务。实验口径上，10 倍压缩比下文字恢复率仍在 90% 以上，说明「微损表示」是站得住的。讲者还介绍了其分级记忆的设想：久远的记忆放进更模糊的图像表示、近期的内容保持清晰甚至纯文本，按层级管理上下文。

Glyph：把压缩真正用于长上下文建模

Glyph 与 DeepSeek-OCR 的分工不同：后者验证可恢复性，Glyph 探索能否用这种压缩真正训出一个长文本模型。整套框架分三步：

  1. 持续预训练：基座选 GLM-4.1V-9B Base。任务有三类——OCR 解析（给渲染图片、直接读出文字）、交错语言建模（文本片段随机渲染成图片做交错建模）、长生成任务（补全开头/结尾/中间）。建模时只渲染 context 部分，instruction 保持文本；后文所有压缩比都只对 context 部分讨论。
  2. 渲染配置搜索：字号、行距、颜色、DPI 等渲染参数对效果影响很大，人工选不完。Glyph 借鉴 AlphaEvolve 的思路，用 LLM 做遗传变异式的配置搜索：人工初始配置集 → 渲染数据 → 在验证集上测基座模型效果 → 把历史配置与性能交给 LLM 分析并变异出新配置 → 循环，实验中跑了约 200 步，并重复多次以避开局部最优。搜出的配置是多任务平均意义上的较优解。
  3. SFT + RL 后训练：SFT 沿用 thinking 格式数据；RL 用 GRPO 做长上下文 QA 等可验证任务。两个阶段都混入一个辅助 OCR 任务——从渲染图片恢复原文——因为输入本质上是「文本变图片」，读得出是做得对的前提，这个辅助任务在消融中被证明不可删。

实验：压缩、性能与效率

  • 主结果：Glyph 在约 3–4 倍压缩比下，在 LongBench、MSL、Ruler 等长上下文基准上与同级领先模型（9B 量级、128K 至 1M 上下文）性能接近，部分任务有提升。
  • DPI 是 test-time scaling 旋钮：在 Ruler 上，DPI 72 时明显弱于基线，升到 DPI 96 后反超纯文本模型——清晰度可以直接换性能。另一个观察是 Glyph 随测试长度增长的性能衰减比纯文本基线更慢；讲者的解释是等效长度论：上下文从 64K 涨到 128K，纯文本模型实际多吞了 64K，而 Glyph 因 3–4 倍压缩只多吞约 16–20K 的等效长度，受长度衰减的影响自然更小。
  • 效率：128K 长度下 prefill 时间大幅减少、decoding 吞吐明显提升，且长度越长加速比越大；训练侧测的是 SFT 加速比，约二点几倍且随长度基本平稳（RL 加速比因 rollout 时长干扰未做公平对比，讲者明说未测）。
  • 跨模态泛化：全程用渲染数据训练的模型，在真实文档版式的 MM-LongBench-Doc 上仍有明显提升，说明渲染训练能泛化到真实任务而非只会读合成版式。
  • 极限压缩：单独用更激进的低 DPI 配置训练后，128K 上下文的模型可以处理 1M 量级的任务，在 MM-LongBench-Doc 上与纯文本模型大致相当，即存在约 8 倍压缩比的潜力；讲者据此展望 1M 模型扩到 4M–5M 甚至 10M+ 的路径。
  • 消融：搜索出的渲染配置比随机组合与人工挑选都更好，平均性能高约 2–3 个点；OCR 辅助任务在 RL 阶段、SFT 阶段逐步删掉都会明显掉点。

讨论与 Q&A 要点

  • 未来工作：自适应渲染（按任务甚至按 query 定制渲染策略，用少量样本快速拟合）；改进视觉编码器——讲者坦言当前 VLM 对 UUID 这类从未见过的独特字符串识别不准、且多页同时输入时 OCR 能力会下降，这是路线的基础短板；用纯文本模型对视觉-文本模型做蒸馏以补齐复杂任务上的差距；把层级化记忆用到 memory 类任务上。
  • 更远的讨论：光学压缩不是唯一选项，latent 表示可能实现更本质的压缩（已有工作称单个 latent 向量可表示上千个词）；讲者还提出一个架构层面的猜想——视觉模型里编码器只有几百 M、解码器是几 B 的悬殊比例，或许提示了一种「小编码器 + 大解码器」的高效建模回归方向，diffusion 模型中 VAE 的近无损压缩还原也是同类思想。
  • Q&A 边界：Glyph 目前在理解类任务上与长文本大模型不相上下，但 agent、复杂推理任务尚未充分测试，个别 case 弱于纯文本模型（拟以文本蒸馏弥补）；后训练阶段不使用纯文本数据，预训练混少量纯文本只是防模型坍塌；压缩比与 DPI 直接挂钩，想要更高压缩就得接受更低清晰度，或像 DeepSeek-OCR 那样用更激进的下采样；持续预训练对算力有要求，后训练几台甚至一台机器即可；两件工作目前都未在生产环境使用（DeepSeek-OCR 是专用 OCR 模型，Glyph 偏学术探索）。

5可迁移

  • 给 agent / RL 轨迹上下文一条新路线：长轨迹的历史部分可以渲染成图像喂给视觉语言模型来等效扩窗，与文本摘要、RAG 式截断互为备选；其前提是配一个「可恢复性」校验（OCR 辅助任务的等价物），否则压缩表示读不准、后续决策全错。
  • DPI 式 test-time 旋钮：同一输入提供便宜（低清晰度）和精细（高清晰度）两档表示、按难度分配，本质是把 test-time compute 做成连续可调参数——这个思路可类比 rollout 预算、采样数在 agent 任务上的分级分配。
  • LLM 遗传搜索做配置工程：渲染配置（字号/行距/DPI）的搜索空间与验证集 fitness 的组合，和 infra 里的采样参数、prompt 模板、数据配比调优是同构问题；200 步量级的 LLM-as-optimizer 进化搜索是一个可直接借用的低成本实现。

6疑问 / 下一步

  • Glyph 在复杂推理与 agent 任务上与纯文本模型的真实差距、以及文本蒸馏能补回多少，讲者明确说尚未充分测试——这是判断这条路线能否走出理解类任务的关键未决项。
  • 主实验配置（3–4 倍）与极限实验配置（约 8 倍）不是同一套，统一配置下「压缩比—性能」的完整曲线 talk 未给出。
  • 多页同时输入时 OCR 准确率下降、独特字符串（UUID 类）识别不准，讲者只给了定性描述，没有量化数字；这是该路线做长程 agent 时最先撞上的基础瓶颈。
