2一句话总结

主流 Agent 框架把一切都序列化进文本上下文，复杂对象只能被压扁成字符串再拼回去，既费 token 又丢结构。CaveAgent 的解法是把持久化 Python 运行时升为 Agent 的主工作空间：语义流只负责轻量推理与生成代码，运行时流以原生 Python 对象保存状态，变量注入/检索让 DataFrame、数据库连接、训练好的模型等对象双向无损流通，交互范式从 Text-in-Text-out 变成 Object-in-Object-out。论文在 Tau2-bench 的 12 个设置中 11 个超过原生函数调用，数据密集任务上总 token 最多低 51%，并指出可检查的运行时状态天然适合做可验证评估与 RLVR 奖励。

3核心

背景/问题：Text-in-Text-out 把对象压扁了

官网预告先点出主流框架的共同约束：无论输入还是输出，所有数据都必须经过文本序列化。CaveAgent 论文把 JSON 函数调用范式的代价拆成三条：

  1. 控制流僵硬：每轮只能发出单个工具调用（或并行批次），结果再序列化回上下文；需要顺序编排的任务被拆成许多往返，延迟与出错点一起增加。
  2. 无状态：每次调用是孤立事务，中间结果必须写回文本才能跨轮保留；复杂数据结构反复序列化带来 token 开销、精度损失与级联错误。
  3. 可组合性差：JSON schema 表达不了循环、条件与变量依赖，多步逻辑只能硬塞进多轮对话。

代码即动作（CodeAct 一类）用 Python 解决了控制流，但界面仍停留在文本：中间状态只能靠 print 输出或文件读写与外部交换，已有的内存对象（如预加载的 DataFrame、训练好的模型）无法直接注入，也无法把运行时对象无损取回供下游使用。CaveAgent 认为真正的缺口不在“能不能跑代码”，而在运行时边界上缺少一等的对象交换机制。

方法/设计：双流架构 + 有状态运行时管理

CaveAgent 把每轮交互拆成两条流。语义流维护轻量的提示内历史，运行时流维护持久的 Python 内核状态：

$$h_{t}=\mathrm{LLM}\left(x_{t},h_{t-1}\right),\qquad\mathcal{S}_{t}=\mathrm{Exec}\left(c_{t},\mathcal{S}_{t-1}\right)$$

这里语义流根据当前输入与历史生成代码，运行时流在上一轮状态之上执行代码并得到新状态。关键不在公式本身，而在两者职责的倒转：传统框架里文本上下文是主工作空间、工具是外设；CaveAgent 里持久运行时才是数据与状态的中心，语义流退化为生成操作代码的轻量编排器。

运行时流（论文 §3.1）

  • 执行内核是一个持久 IPython 交互式 shell，可以把每轮看成虚拟 Jupyter notebook 的一个 cell。全局命名空间里的变量、函数与导入模块都会跨轮保留，后续代码直接引用变量名，不需要模型把值背进上下文再复述出来。
  • 工具不是文本描述完就结束：它们作为活的 Python 对象注入初始命名空间，Agent 直接调用对象方法、修改对象内部状态，状态跨轮持续。
  • 大对象（DataFrame、图结构、规划树等）整体留在运行时内存里，语义流只持有变量名与轻量描述。这就是论文所说的 “Code as Action, State as Memory”：代码是动作，运行时状态是记忆。

变量与函数注入（论文 §3.1.1）

每个可注入实体会被包一层容器，自动抽取元数据：函数的签名、类型注解与 docstring，变量的名字、类型与描述。这些元数据汇总成一份轻量 API 参考放进系统提示，真正的对象则直接映射进执行命名空间。于是模型看到的是“有哪些对象、各能做什么”，而不是对象本身的全文。交互也因此变成面向对象式：直接在状态对象上链式调用方法，用原生循环与条件组织逻辑，最终交付原生 Python 对象，而不是一段待解析的文本近似。

动态上下文同步（论文 §3.1.2）

语义流默认“看不见”运行时状态，必须显式生成代码去取（例如只打印 DataFrame 的前几行）。论文称之为 Active Attention：只有被主动取回的相关切片才进入 token 上下文。执行输出经过 Observation Shaping 的长度约束，超限时返回结构化提示，要求 Agent 改用汇总方法。这个闭环专门防“上下文爆炸”：重数据留在运行时，轻量推理走语义流。

安全检查（论文 §3.1.3）

生成代码执行前先过基于 AST 的静态分析，规则模块化：ImportRule 拦截未授权模块，FunctionRule 禁止 eval 一类危险调用，AttributeRule 防沙箱逃逸。违规时把结构化错误返回语义流，让 Agent 自我修正，不中断整个交互。需要注意这只是执行前的静态过滤，不是完整的沙箱与审计系统；论文部署讨论也承认审计级工具（责任链日志、不可变运行历史）仍是未来工作。

运行时集成的 Skill 管理（论文 §3.2）

CaveAgent 扩展 Agent Skills 开放标准：在标准 SKILL.md 之外增加 injection.py。标准 Skill 只给文本提示；CaveAgent Skill 在激活时还会把函数、变量与类型定义直接注入持久运行时。启动时只加载名称与描述等元数据做路由，完整说明与运行时注入在调用激活时按需加载（progressive disclosure）。这样领域能力可以同时以“给模型看的说明”和“给运行时用的可执行工件”两种形态分发，工具注册与技能分发被统一成一个机制。

多 Agent 协作与 RLVR 接口（论文 §3.3 以降、第 5 节）

同一运行时底座还支持以状态而非消息做多 Agent 协调：主 Agent 可以把子 Agent 当作一等对象注入自己的运行时，程序化地设置变量、触发执行、取回结果；多个 Agent 也可以共享同一运行时，一个 Agent 修改共享对象，其余 Agent 通过直接引用立即看到。论文对这部分只给了定性案例（城镇模拟、AutoML 训练环），并明确把严格定量评估留作未来工作。

对 RLVR 的意义在于可验证性：运行时状态在任意时刻都可被程序化检查，评估器可以直接断言中间变量与最终对象的类型、数值与结构，而不必解析文本输出或依赖人工标注。这为细粒度奖励与自动评估提供了结构性接口。但要分清事实与愿景：论文展示的是“状态可检查”这一架构性质与若干案例，并未真正跑一轮以 CaveAgent 为环境的 RL 训练。

实验/实战：标准基准、状态管理与 token 效率

Tau2-bench 多轮工具使用（论文 §4.1.1）

评测覆盖 6 个模型（DeepSeek-V3.2、Qwen3-Coder 30B、Kimi-K2-0905、Claude Sonnet 4.5、GPT-5.1、Gemini 3 Pro）的 Airline 与 Retail 两个域，每格 3 次运行。CaveAgent 在 12 个“模型 × 域”设置中 11 个超过该模型的原生函数调用。增益集中在状态密集的 Retail 域：Qwen3-Coder 从 41.2% 提升到 54.7%（+13.5），Kimi-K2 从 60.8% 提升到 71.3%（+10.5），Gemini 3 Pro 在 Airline 提升 +6.7、Retail 提升 +5.5。唯一的回退是 Claude Sonnet 4.5 的 Airline（57.3% → 56.7%，−0.7）。论文同时给了方差分析：每格只有 3 次运行，若干 Airline 小增益落在运行间噪声范围内，Retail 的主要增益更稳健。这个保留意见重要：CaveAgent 的优势被论文自己限定在“多轮、状态密集”的工作流，而不是所有函数调用场景。

BFCL 原子函数调用（论文 §4.1.2）

在 BFCL v3 的 4 个 AST 评测类目共 1,000 条样本上（论文明确排除了 live、多轮与多步子集以免与 Tau2-bench 重叠），三个开源模型在 CaveAgent 下都达到 94.0–94.7%：DeepSeek-V3.2 从 86.9% 提升到 94.0%，Qwen3-Coder 从 89.8% 提升到 94.4%，Kimi-K2 从 89.2% 提升到 94.7%；与闭源模型的原生函数调用相比，Claude Sonnet 4.5 为 94.4%（持平）、Gemini 3 Pro 为 94.3%（持平）、GPT-5.1 为 89.6%（其 CaveAgent 结果 88.9%，略低）。论文据此提出一个值得注意的判断：对代码能力强的模型，函数调用协议本身可能与模型规模同等重要地构成性能瓶颈。

状态管理专项（论文 §4.2）

论文自建了以程序化校验为原则的状态管理基准，直接检查执行后的运行时状态而非文本输出。三个维度的结果：类型熟练度（简单类型、自定义对象、科学计算类型）96.5–100%；多变量管理（5–25 个并发变量）90.9–100%；多轮持久性（两个各 40 轮的场景）81.3–98.7%。论文也坦承前两个维度多数模型接近天花板、区分度有限，其作用是结构验证；真正拉开差距的是 40 轮状态持久性。这组实验支撑的是“运行时确实管得住状态”，不是模型排行榜。

token 效率（论文 §4.3–§4.4）

在 IoT、金融、电商三个逻辑互依赖的域上，DeepSeek-V3.2 的总 token 从 JSON 函数调用的 704,188 降到 CaveAgent 的 504,119（−28.4%），步数从 236 降到 145，成功率从 94.6% 升到 100%。论文强调节省主要来自 prompt token：代码更啰嗦使 completion token 反而多 36.3%，但跨轮累积的 prompt 才是总账大头。按成功轮次归一化后，三个模型的 prompt 节省分别为 DeepSeek-V3.2 +37%、Gemini 3 Pro +30%、Qwen3-Coder +48%。

数据密集场景（30 个任务、2020–2025 年苹果与谷歌股票数据）同时构成部分消融：去掉注入/检索接口的 CodeAct 风格在 Data Query 上从 100% 掉到 80%、Visualization 从 90% 掉到 40%；再去掉代码执行的 JSON 函数调用在 Data Analysis 上只有 10% 且耗 130 万级 token。CaveAgent 相对各任务最佳基线的总 token 降幅分别为 Data Query −51%、Data Analysis −2%、Visualization −39%。这组结果把两个组件的贡献分开了：代码执行解决“算不动”，注入/检索解决“对象进不来、取不回”。

结论/观点：区分论文事实与作者判断

论文事实层面的结论是：在多轮、状态密集、对象复杂的任务里，把状态管理从文本上下文卸载到确定性的持久运行时，能同时提高成功率与 token 效率；程序化可检查的状态还为自动评估与奖励生成提供了接口。作者的判断（观点层）更强：他们认为 Agent 的主工作空间应当从 LLM 的文本上下文转移到运行时，LLM 的角色从“文本生成器”转为“运行时操作员”，技能分发也应从给文本提示升级为交付可执行工件。

论文自己给出的边界同样明确：适合的场景是多轮长状态、不可序列化或精度敏感的输入、多 Agent 状态交接、需要中间状态审计的任务；短单轮查询下 JSON 函数调用的内存与冷启动成本更低，未必值得换。部署层面，持久内核有基础内存占用与首轮内核启动成本，长会话的内存增长需要显式删除变量或会话检查点来管理，这两点在论文里都只是给出了设想、没有实测量化。

5可迁移

  • 对 coding data / RL infra 工作的直接可试点：给 Agent 运行时加一等的“对象句柄”层——中间产物以带类型与元数据的运行时变量保存，prompt 里只放名称、签名与摘要，评估器直接读最终对象与关键中间状态做断言。对 coding agent 来说，这意味着测试结果、代码对象、数据表都不必再被打印成文本喂回去；奖励也可以从“解析最终回答”改成“检查工作区状态是否满足条件”，与 RLVR 的可验证奖励天然同构。
  • Infra 视角：状态存储与转录（transcript）应当分开建模。运行时命名空间要有生命周期管理（变量删除、会话检查点、内存配额）、安全分层（静态检查之外还要资源限额与审计日志）与跨会话序列化；Skill 则可以按 SKILL.md + 可执行注入工件的双形态打包、版本化。论文给的选型标准可直接借用：多轮长状态、不可序列化输入、多 Agent 交接、需要中间状态审计，四条占得越多越值得上这套架构；短单轮任务继续用 JSON 函数调用更划算。

6疑问 / 下一步

  • 没看懂的 / 想深挖的 1 个问题：安全边界。AST 静态检查能拦显式危险调用，但动态属性访问、第三方包漏洞、无限循环与资源耗尽、跨会话的状态投毒都不在它的覆盖内；把持久运行时放进多租户生产环境时，内核隔离、配额与恢复策略要做到哪一层，论文只给了部署设想，没有实测——这是落地前最想深挖的一点。
  • 并发与规模未验证：论文的多 Agent 共享运行时是单线程、轮次化的，靠线性化更新避开消息顺序歧义，但也牺牲了 Agent 间并发；多租户、大对象量级下的内存与冷启动成本均未做生产级剖析。
  • 现场内容不可还原：讲者对 RLVR 一节的展开（官网提纲第 3 节）、数据分析与可视化等演示、未来方向与 AMA 无法从论文推知；若后续取得可验证字幕，应以字幕为准修订。
