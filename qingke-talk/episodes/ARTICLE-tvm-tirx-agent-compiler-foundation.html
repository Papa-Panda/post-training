2一句话总结

Agent 已经能自动开发高性能 kernel 与框架优化，编译器作为"编译东西"的工具正在被绕过，但陈天奇认为编译器本身依然重要、只是必须换形态：把其中稳定、轻量、可预测的底层抽出来做成 TVM-TIRx 基础层（轻量核心 IR + 稳定底层模块 + 动态扩展 + 三语言混合驱动 + 对接成熟工具链），让 agent 在上面快速构建上层编译器与分析工具。

3核心

  1. 背景/问题：2026 年是 Agent 元年，机器学习编译与 kernel 开发感受最深。传统 ML 编译靠领域知识在图、tile、SIMT 各粒度做优化；如今只要 token 足够，底层算子与软件基本都能由 agent 蹬出来，近期 KernelAgent、CUDA Agent、CAKE、KDAgent、EAT 等工作在自动化 GPU kernel 开发上进展显著，人类也终于能从读 nsight 报告、查汇编、手动微调 kernel 的循环中解脱。但随之而来的问题是：agent 开发 kernel 的水平超越人类基本是必然，我们是否在淘汰我们自己？HazyResearch 的《Retire the Abstractions》甚至开始质疑是否还需要 CUDA DSL。当编写程序的主力不再是人类，编译器还存在吗？
  2. 判断：还需要，但形态要变：作者的答案是编译器本身依然重要，但是必须以不一样的形态出现。即使 agent 能直接出 CUDA/PTX 乃至汇编，仍有两个绕不开的需求：程序分析（结构化表示是 agent 快速构建分析工具、收集迭代反馈的凭借，就像人会心算但仍借助计算器）和程序验证（正确性需要严格检查与验证，某种结构化的程序表示是必要条件）。所以未来"我们可能不再需要编译器去编译任何东西，但是我们依然需要编译基础架构来帮助我们分析和验证程序本身"——一个相对通用的 IR 成为分析、验证与 agent 构建额外工具的基础层。
  3. 方法/设计（TIRx 基础层的五元素）：在 TVM FFI 发布一年后，团队继续模块化 TVM 核心，拆分并针对 agent 从头重新设计打磨出轻量级独立仓库 TVM-TIRx，包含：
  4. 轻量级的核心 IR 集合，用于 DSL 和编译中的常见需求与快速扩展；
  5. 稳定的可复用的底层模块，负责编译过程中比较"老实"和可预测的部分，剥离高层需要 heuristic 的部分；
  6. 优先支持动态扩展，扩展 DSL 类型和操作本身可以直接在 off-tree 的包里完成，并动态链接 import 基础层；
  7. Python、Rust、C++ 三语言自由混合驱动，给 agent 足够灵活度按场景选择语言开发编译器；
  8. 对接稳定的底层编译工具链，在保持足够灵活度的前提下对接成熟工具链，把 token 花在该花的地方。 总体形态：从原来单一、heuristic 与确定性变化混在黑盒里的编译器，变成更模块化的组合方式，并且给 agent 提供直接针对 IR 数据结构等内部模块的直接访问，方便 agent 自己开发扩展。
  9. 三个设计问题的取舍：
  10. 是否所有模块都用同一种语言？ 成熟编译器多围绕一门核心语言建、再包 wrapper；但 agent（人也有类似经验）开发时，POC 与快速开发用 Python 最顺手，需要效率或更强类型检查给 agent 反馈时 Rust 与 C++ 更自然。理想是让 agent 在模块级别自由切换语言：TIRx 以 TVM-FFI 为基础 ABI，完成了 Python、Rust、C++ 三语言自由混合驱动，agent 可在 Python 做原型，再把需要的部分在 Rust 或 C++ 中实现，并混合调用任意语言实现的其它变换与分析模块。其中 Rust 支持是"世界上第一个比较完美支持 Rust 和 C++ 直接混动开发机器学习编译器"的尝试。
  11. 如何让聪明的 agent 更快迭代？ 编译器项目编译时间长，agent 每次扩展都要改大仓库代码、重编整个编译器、跑测试、失败重来。解法是优先支持动态扩展：以 everything as plugin 的方式在独立 repo 迭代，agent pip install 基础层后快速迭代需要的部分。技术上需要仔细设计基础架构：常见 visitor pattern 要求提前知道所有可能的类型节点（这也是 Rust enum 与 LLVM/MLIR 需要静态编译的原因），要支持动态增加类型并保留递归访问、改写、符号表达式约束传递等功能，需要基于 TVM-FFI 的结构化 API 设计。动态扩展支持、独立模块化、符号表达式 Z3 约束等均来自 TileLang 社区对 TIRx 的反馈与支持。
  12. 未来怎么维护代码？ 软件都是 agent 蹬出来之后，仍需维护不同领域相关编译代码，也有 compiler harness 这类以分析而非变换为主的工具需求。核心矛盾是快速迭代与代码 slop 化之间的矛盾，且不同模块对迭代速度与 slop 的容忍度完全不同：kernel 迭代可以每几分钟出一个、最后审核前完全无人干预；希望复用可靠代码的部分仍需更多人工审核（或在优化架构的前提下投入大量 token polish）。因此传统项目模块必然按稳定性与迭代速度需求分层，基础层的职责就是负责编译中比较轻量、稳定、"老实"的部分，一旦需求确定不需要特别多针对 heuristic 的调整，同时保持足够灵活性给 agent 扩展编译抽象，让 agent 基于基础层做高层编译器扩展与 compiler harness 快速迭代。
  13. 结论/观点：今年是技术十字路口，未来很难预测，文中形态不一定是 Agent 时代 ML 编译技术的唯一可能形态。但两点肯定：原有抽象与设计都需要被重新审视；过于限制的抽象会让 agent 开发遇到上限瓶颈，一定不能限制 agent 的上限，而有结构且保留灵活可扩展组合边界的设计能让 agent 进入更快的开发迭代流程。TVM FFI 的模块化是去年走出的第一步，TVM TIRx 的模块化是向着这个方向的又一步。

5可迁移

  • 对 post-training / RL infra 工作：TIRx 的"稳定基础层 + 动态扩展"分层思路可直接借鉴到 RL 训练框架设计——把确定性、可验证的部分（权重同步、数据流、verifier 接口）钉死成稳定 ABI，把 heuristic 与快速迭代的部分（reward 设计、采样策略）做成 off-tree 可插拔模块，避免每次改策略都要重编整个大系统。
  • Infra 视角：把 token 花在刀刃上——对接成熟工具链解决非瓶颈问题（如 host 代码生成优化），只把 agent 的 token 与迭代预算投到真正需要定制的部分；同理，RL infra 里把成熟组件（Megatron、SGLang）当作已解决的底层，精力投在训推一致性与数据流这些真瓶颈上。
  • 评测自动化启发：编译器基础层存在的核心理由之一是"分析与验证"——RL infra 同样需要先建 verifier 与分析工具（轨迹检查、KL 监控、熵曲线），再谈算法迭代速度，否则 agent/训练跑得越快，错误埋得越深。

6疑问 / 下一步

  • TIRx 的轻量核心 IR 与 MLIR/LLVM 的 dialect 体系如何分工？动态扩展的类型系统在 agent 频繁注册新 op 时，如何保证类型安全与符号约束求解的可判定性？
  • 三语言混合驱动在真实 agent 迭代中的 token 成本：Python 原型 → Rust/C++ 落地的切换点由谁判断，是否有可量化的切换准则？
