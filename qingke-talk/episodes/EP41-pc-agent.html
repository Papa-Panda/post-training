2一句话总结

PC-Agent 把复杂 PC 指令拆成「指令 → 子任务 → 动作」三层，用 manager / progress / decision / reflection 四个多模态 agent 分工执行，并用 accessibility tree 加主动感知模块补上通用多模态大模型在 PC 场景的两块短板——密集小图标的 grounding 与富文本布局理解；在自建的 PC-Eval 上拿到对比框架中的最佳成绩，但完整指令成功率也只有 50% 出头（字幕口径），讲者明言这是框架缝合式方案、终局是把四种能力训进一个端到端模型。

两个难点：PC 不是放大版的手机

讲者的立论从与自家 Mobile-Agent 的对比开始。PC 场景比手机难，两难都在「生产力场景」：

  1. 感知难：屏幕大、交互元素密集多样（Word 功能区全是小图标且无文字说明），像素级小图标的理解与定位对多模态模型是硬挑战；Word/Excel 这类富文本的布局理解（「把倒数第一段文字加下划线」）更是普遍做不对。讲者实测口径：针对若干应用收集约 100 条 grounding 数据，当时 GPT-4o、Claude 3.5 的定位效果都很差——这是多模态大模型的通病（Qwen2.5-VL 因混入大量此类预训练数据而明显更好）。
  2. 决策难：PC 指令是办公/生产力型的长序列、跨应用工作流（看 Outlook 邮件 → Chrome 查攻略 → 写进 Word → 算日期），子任务间有信息传递与依赖，远长于手机的娱乐型短任务。

感知层：a11y tree + 主动感知，用「先读出文字」绕开布局理解

  • Accessibility tree（a11y tree）：借用 Windows/macOS 系统自带的可访问性树，框出页面全部可交互元素，并带上软件预置的功能描述（如关闭图标旁注「关闭」）。框的来源是系统数据而非模型预测，讲者在 Q&A 中强调其准确率从设计上就有保证。
  • 主动感知模块（APM）：专门处理模型读不懂的富文本布局。做法是加一层桥：先让 intention-understanding agent 把目标文本段落整段「读出来」（把定位问题转成模型擅长的 OCR 问题），再用 OCR 工具回定位这段文字的左上/右下坐标，最后用 drag 动作选中。端到端定位被拆成「读出 → 定位 → 操作」三步降难度。
  • 决策时给模型的输入是双路的：带可交互框标注的 SoM 截图 + 主动感知产出的文本与坐标信息，一并交给 decision agent。

决策层：三层拆解 + 四个 agent + 一个结构化 hub

框架是「自上而下执行、自下而上反馈」，四个 agent 各管一层：

  • Manager agent（指令层）：把复杂指令拆成子任务，并维护一个 communication hub——子任务间要传递的信息（会议时间、地点、步行时长等）不写在自然语言记忆里，而是解析成 JSON 式的结构化数据存取，manager 负责把上游子任务的输出填入下游的输入。
  • Progress agent（子任务层）：跟踪当前子任务的执行进度（哪些步骤已完成），避免把冗长的历史 action 全堆给决策模型造成干扰与压力。
  • Decision agent（动作层）：结合感知输入与进度信息，输出三件套——思考（thought）、具体动作（action）、给 progress agent 用的简短 summary；动作经 pyautogui 落到键鼠操作上执行。
  • Reflection agent（反馈回路）：输入操作前、后两张截图，比较变化判断动作是否达到预期（单张图无法判断预期是否达成），成功则回写 communication hub 并推进，失败则把反馈给 decision agent 改动作。讲者给的案例很能说明其价值：连续搜索时 agent 误点失效的「前进」箭头卡死，反思发现前后截图无变化后报错，决策改用 Ctrl+T 新建标签页完成第二个搜索。

消融（字幕口径）：主动感知、manager、reflection 三个组件对整体都关键，缺一明显掉点——讲者以此呼应他开篇的智能体定义：memory、planning、reflection 缺一不可。

评测：PC-Eval 与「50% 出头」的诚实成绩

  • PC-Eval：团队自建并开源的测试集，覆盖 8 个常用 PC 应用、25 条复杂用户指令，每条由多个有依赖关系的子任务组成，强调精细图标操作与长程决策；讲者认为 OSWorld、WebArena 的生产力子集仍不够贴近真实工作流。
  • 结果（字幕口径）：端到端单模型能完成前一两个子任务，但完整指令成功率很低；多 agent 框架（UFO、Agent-S）整体优于单模型，PC-Agent 最佳，但完整指令成功率也只有 50% 多。两个对照框架的短板被点名：UFO 擅长操作系统设置类任务、但依赖 API 调用，在用户真实浏览器里（无 Playwright 时）表现差；Agent-S 子任务拆得过细、依赖关系复杂反而拉低成功率。换基座实验中 GPT-4o 最佳；reflection 成功率（recovery rate）以 Claude 与 GPT-4o 较高，manager 的拆分正确率（人工核查）亦然。
  • 延迟账（字幕口径，Q&A）：基于 GPT-4o 一类 API 时，decision 一次约 30 秒、reflection（双图输入）约 40 秒、progress 约 10 秒——两个动作之间实际运行时间很长。这是讲者力推端到端化的直接理由：把感知、决策、反思训进一个模型，单步调用压到 10–20 秒甚至 5 秒级。

定位：坚持键鼠 + 多模态，终局是端到端 RL 模型

讲者在热点对照一节给出的路线判断（观点，非实验结论）：

  • 键鼠操作不放弃：Operator、Manus 的经验都说明，API 不开放/需高权限的场景大量存在，键鼠是最通用泛化的执行方式；未来是「键鼠 + API 结合」（先从浏览器插件/API 入手），纯文本 LLM 路线读不懂的布局必须靠多模态补。
  • 框架只是过渡：当前多 agent 框架有大量 handcrafted 成分；团队正在探索用 DeepSeek-R1 式 RL 流程（讲者提及 GRPO 等策略）训一个端到端 agent 模型，把决策与反思等模块融进单个模型。讲者判断 agent 场景的 RL 训练还能反哺通用推理能力。
  • 其他方向：操作上云（云端执行不占用用户本机，Manus 的关键产品点）、快操作与慢思考结合、手机与 PC 端信息联动（个性化偏好多存在手机端）、语音交互前置模块（已在开发）、端云结合的隐私方案（感知模型放端侧、只上传感知结果）。

开源形态（字幕口径）

Mobile-Agent 仓库含 Mobile-Agent v1（2024 年 1 月，端到端）、v2（planning/decision/reflection 三 agent）、v3、Mobile-Agent-E（自我进化、执行中总结 tips/shortcut）与 PC-Agent v1/v2；PC-Agent 已同时支持 Windows 与 macOS。几个实用配置：add_info 字段注入操作知识或用户偏好（如点咖啡不加冰）可显著提高成功率；简单任务可关 reflection、跳过任务拆解（simple 模式）提速。

5可迁移

  • Communication hub 的结构化传递：多步 agent 工作流中，子任务间传 JSON 结构化状态而非自然语言记忆转述，可显著降低信息在转述中的损耗与幻觉——适用于任何 manager/worker 式 agent 编排。
  • 「先读出、再定位」的感知降难度法：把模型不擅长的布局定位问题转成其擅长的 OCR/生成问题，再用工具回定位坐标。对 GUI 自动化、文档处理类 agent 是通用技巧。
  • 前后截图对比做反思：判断动作是否生效要看状态差分而非单帧，这一点对一切 GUI/环境交互 agent 的 verifier 设计都成立；且反思的收益在长程任务上才显现，简单任务应可关（对应其 disable_reflection 配置）。
  • 延迟预算观：多 agent 串行调用的单步延迟是框架方案的硬约束（本期约 80 秒/步量级，字幕口径）；做 agent infra 时应把「每步几次模型调用、每次多久」作为一等公民指标，它直接决定端到端化的必要性。

6疑问 / 下一步

  • PC-Eval 只有 25 条指令，50% 出头的成功率统计噪声较大；且评测由团队自建自测，与 OSWorld 等公开基准的交叉验证未在 talk 中给出。
  • 框架对手工设计的依赖（子任务拆分、hub 字段、add_info 注入）与讲者主张的端到端 RL 终局之间的路径未展开：RL 训练需要可交互环境与奖励信号，PC 真实环境里这两者如何规模化获取，talk 未涉及。
  • Reflection 以截图差分判成败，对「动作生效但页面变化微小/延迟加载」的场景鲁棒性如何，未讨论。
  • a11y tree 依赖应用与系统提供可访问性数据；对自绘 UI（游戏、专业软件）覆盖如何，talk 未展开。
