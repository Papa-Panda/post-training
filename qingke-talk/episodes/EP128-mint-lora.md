## 一句话总结

MinT 把 LoRA adapter 而非完整基模做成训练、评测与上线的核心对象：基模常驻 GPU，训练与推理之间只交接数百 MB 量级的 adapter，从而在同一套路径上支持 0.6B 到 1T 的基模、百万级 adapter 目录与多策略交错训练；针对 MoE 与稀疏注意力的训推不一致，分别用 R3 路由重放与 IcePop 式 token 降权/丢弃做工程化稳定。

## 核心

### 为什么需要百万级 LoRA：从「一个任务一个微调」到「一个基模挂海量 adapter」

讲者先把 LoRA 的常规介绍收个尾：冻住基模、只训一个低秩矩阵来调整行为。但本期要看的是另一个维度——**同一个基模上挂载多个不同的 LoRA**。字幕中列了三类场景：

1. 领域专家：除代码任务外，法律、金融等领域都需要处理专业知识的专家 LoRA。
2. 产品个性化：每个用户表达偏好不同，可以用不同 LoRA 对不同用户做个性化。
3. 工程迭代：同一任务做多种实验、多个候选与 AB 测试、以及对整个训练迭代过程做完整快照。

当 LoRA 数量从个位数变成成千上万甚至百万级，就不能再为每一个 LoRA 复制一套基模——这是 MinT 要解决的核心问题。讲者把 MinT 定位为 LoRA 后训练与推理的统一运行服务，简单说就是 "LoRA as a Service"：用户只关心基模选型、训练数据、训练范式（SFT / RL / DPO）与评测指标，GPU 集群分配、模型状态管理、分布式并行与编排等工程细节由 MinT 封装，不应成为使用门槛。

系统的工作闭环是一个 RL 循环：training worker 更新权重并写入 LoRA population（包含大量不同 adapter 的池子），rollout 侧从 population 中取最新 adapter 采样，采样数据再送回 training worker 做下一轮迭代。关键点是基模一直在 GPU 上驻留，每次训练与推理之间交接的只是 LoRA 这一部分权重——对万亿参数规模的大模型来说，也就是数百 MB 而不是数百 GB 的文件尺寸。讲者由此引出三个扩展维度，并给出 adapter 参数占比的口径：在千问三 4B、rank 32 的 adapter 上实测，单个 adapter 约占基模参数量的 3% 左右；对更大基模若只做少量风格调整，rank 可以更低、占比还可以更低。这条路径已在 MinT 上基于 GLM 5.1 训练出用户助手类 agent 模型「马卡龙 V1」，并对 GLM 5.2 的微调做了 day-0 支持。

### Scale down：只交接 adapter，RL 每步交接的成本被压下来

传统全参数微调训练完要把整套权重从训练侧搬给推理侧；即便用 LoRA 训练，若训练完把 adapter 与基模权重合并再交付，交付的仍是一个完整模型，合并与传输都有成本。MinT 的做法不同：基模已在 GPU 上驻留，训练完只需传输挂载在基模上的 LoRA adapter。讲者给出实测口径：在小模型上交接时间可加速高达十几倍；模型越大，传输时间的相对倍数不像小模型那么明显，但节约时间的绝对值更大，大、小模型都有明显加速。这个加速在 RL 训练中尤其重要，因为 RL 的 rollout–update 循环每一步都要做一次交接，反复交接省下的时间非常可观。

### Scale up：同一条路径从 0.6B 到 1T，以及 MoE / DSA 的训推不一致

MinT 号称用同一套 RL 训练路径支持从 0.6B 一直到 1T 的模型，共支持 6 个模型家族、27 个变体、4 种不同架构；讲者称其团队是「全世界除了智谱以外，第一个在 GLM 最新模型上进行后训练的团队」，且这与 MinT 的支持分不开。

规模上去后第一个难点是 MoE 的训推不一致。MoE 每层有多个 expert，router 决定每个 token 送到哪个 expert；推理时某 token 被送到 expert 2，训练时因 router 前的数值误差被送到另一个 expert，两边的梯度就对不上，导致严重的训推不一致，且经多轮训练逐渐累积。讲者给出架构对比：在千问三这类架构上训推不一致还能控制在合理水平，但用 Moonlight 16B（DeepSeek V3 架构的小模型）时，随着训练推进训推不一致越来越大，直到整个策略崩溃。原因是 DeepSeek V3 架构的 router 对每个 expert 独立打分，得分接近时微小变化就可能翻转排名，路由选择结果关于前面的数值误差是不连续的。

解法是 **R3（replay router routing）**：推理时把每一个 router 的选择记录下来，训练时强制重放同一条 routing。讲者强调实验表明这对高效训练 LoRA 模型非常重要：使用 R3 后 training 与 rollout 的概率分布一直保持较好对齐（mean probability difference 保持平衡），在 Math 任务上只有使用 R3 后 validation accuracy 可以持续上升；若只用 baseline 或简单的 importance sampling 做训推不一致缓解，reward 会越训越差，在 DeepSeek V3 架构模型上做 LoRA 时无法得到有效训练。

第二个难点来自 **DSA（DeepSeek Sparse Attention）**，即 GLM 5.1 等 DeepSeek V3.2 架构新模型使用的注意力机制。DSA 有一个 indexer 机制，在每一步选择哪些历史 token 参加 attention；与 MoE routing 类似，由于前期数值误差累积，离散的选择状态会变化——例如 rollout 时对历史 token 1、3、5 做了选择，训练时却变成 2、3、4，最终当前 token 的概率就很不一样。与 MoE 的区别是：MoE 的 router 每层只做一次决定、数量较小，可以 replay；DSA 里对每一个 token 都需要 indexer 做选择，决策数量远大于 router，完整的 replay 不可行，需要一种不依赖 replay 的稳定化方案。讲者的方案参考了 GLM 5 / 5.1 原始技术报告，思路是 **IcePop**：对训推不一致严重的 token 进行降权或者丢弃，从而稳定梯度。实测口径是：baseline（虚线）整个 grad norm 大幅波动、训练非常不稳定；使用 IcePop 选择性丢掉训推不一致特别差的 token 后，grad norm 保持平稳，训练可以正常收敛。讲者坦言这不是一套完美的方案，但在工程上非常可行，他们在 GLM 5.1 的 LoRA RL 训练中使用该方法获得了非常好的后训练效果。

### Scale out：百万级 adapter 的三级驻留与加载

当 adapter 到达百万量级，如何管理它们？讲者的思路是三级缓存 / 三层驻留机制：

- 最底层是持久存储，承载整个 100 万量级的 LoRA 目录 catalog；
- 中间是 CPU 内存缓存，单台机器上大概可以存 500 个最近使用的 adapter；
- 最上层是 GPU，可同时进行推理的 adapter 可能就是几十个或者更少。

加载效率上做了两点优化：一是对 MoE 模型 LoRA 中很多小的 tensor 做打包，加载时能形成 8.5 倍左右的提速；二是新的 adapter 在后台预热，不影响在线正在使用的用户。为什么需要三层？讲者给出实测数据：CPU 缓存命中时，把一个 LoRA 加载进来的 P95 延迟只有约 21 秒（字幕口径；该数值明显偏大，疑为字幕识别或讲者口误，原文如此，读者请结合上下文理解为「命中时延迟远低于冷加载」），而缓存未命中、从冷存储加载一个 LoRA 可能需要 200 多秒，两者差了整整一个量级——这正是三层设计的驱动力。把 catalog 从试验性的 1000 个扩到真正关心的 10 万量级后，warm（已在 CPU 上加载）的延迟基本不变，说明 catalog 规模本身不是大瓶颈，关键是系统如何设计以更好地命中缓存、让当前真正需要使用的 LoRA 尽可能快地加载进来。冷加载的边际成本是每个 LoRA 大概一点几秒，呈线性增长、可预测，这也是更大规模 scaling 的理论基础。基于这套设计，讲者称已成功 serve 百万级别的 LoRA，其中没有任何系统错误，大部分请求 P95 在几十秒这样相对可接受的量级。

推理侧与训练侧使用 adapter 的方式不同：推理侧是空间维度的 multi-LoRA——一个推理引擎同时持有多个不同 adapter，不同请求路由到不同 adapter、共享一个基模，可以在一个 batch 里同时处理；训练侧是时间维度的 multi-LoRA——同一个 trainer、同一个基模分时切换不同 policy 的 LoRA 及其对应的优化器状态。例如 LoRA A 这个 policy 等待 rollout 时，trainer 就切到 LoRA B 去做更新，减少 GPU 空闲。为什么训练侧不用空间切分？一是训练数据量往往比较大，单个 LoRA 就可以打满整个 GPU 的显存和算力，不像推理那样有必要靠同时处理多个 LoRA 提升效率；二是算子支持层面上目前还有一些 gap。讲者同时说，训练上支持多个 LoRA 真正在时间上并行训练是可以的，也是他们正在做的工作，之后会在 infra 上不断创新以提升多策略并行训练效率。多 session 交错调度的实测结果是：在测试任务上，千问三 4B 训练三个 GRPO 策略的总时间从 51 分钟压缩到 29 分钟，加速将近两倍；在千问三 30B 这个 MoE 模型上也有类似加速效果，且峰值显存完全不变——因为基模一直驻留，只是切换 adapter 在训练；峰值显存与算力占用类似，但分时切换极大减少了 GPU 中的「泡泡」，提高整体利用率。

### 第三条扩展轴：数量，以及马卡龙与行业验证

讲者在技术细节之后退一步看大模型发展主线：过去更关注两条 scaling 轴——扩大模型规模（更多数据训更大参数规模的模型），以及扩展模型能力（通过 RL 在规模下不断后训练，学会更好的推理与行动）。讲者认为同样重要的还有第三条轴，也就是**数量**：未来可能不是训一个大模型试图解决所有问题，而是在同一个基模基础上训练海量的 LoRA 来做领域分工、个性化演化以及模型之间的继承与组合。给出的数字是：可以使用 1T 的基模，但每一个用户、每个版本只需要最多 5B 的 LoRA；现在在线产品上已经有数十个 LoRA 在同时运行，用户在产品中创建了 30 万规模的不同小应用来满足个性化需求。

MinT 支撑的 C 端产品是「马卡龙」——用户个人助手性质的 agent 小应用，也是 MinT 的第一个规模化验证。愿景是 "one person, one LoRA"：MinT 支持的百万 LoRA 恰好对应百万用户规模，希望记住每一个用户的个性化能力、偏好，生成定制化 UI，适应每一个用户的对话风格。已上线的 agent 模型「马卡龙 V1 preview」被讲者称为全球首个在 GLM 5.1 上完成 LoRA RL 的 agent 模型：744B 的 GLM 5.1 基模加上 6B 的 LoRA（字幕口径作「470 744B」，此处按 744B 理解）。该模型天生支持 Mixture of LoRA 范式——针对不同任务训练多个不同 LoRA、在线对它们进行路由；在生成式 UI 编码、多轮聊天、长链路推理以及工具调度与交接上都取得了非常好的效果，并能和同类模型匹敌甚至超过。MinT 还支撑了 A2UI 技术（agent 生成可交互界面而不只是文本），这是马卡龙 app 的核心能力：传统方式是用户反复和 AI 聊天澄清需求，A2UI 是 AI 直接生成带选择器和滑动条的可交互卡片，用户点选偏好来和 AI 沟通；这个能力是在 GLM 基模上通过 LoRA RL 训练出来的，模型已在 Hugging Face 上开源。

同一套「基模 + 不同 LoRA」的范式已在六个行业场景中验证，讲者逐项给数：在医疗相关的 coding 任务中把 GPU 成本降低了 90%，有 8000 多个医生在使用这样一个产品选出的定制模型；在金融客服场景中客户满意度提升了 34%，合规度也有大幅提升；在政务中政策更新周期缩短、转人工率明显下降；在最关心的个人 agent 上，不同用户创建了 30 多万个小程序；法律领域用其提供的 recipe 进行了 SFT 与 RL 训练；甚至在具身智能中，VLA 以及世界模型也可以基于 MinT 这样一套架构进行训练。

### 开源生态与使用方式：让 coding agent 自己跑通 MinT

MinT 的一些核心组件已贡献到开源社区，讲者重点提到提供了可自行部署的 MinT 服务包（集成到 vLLM 生态），同时提供客户端 SDK 与快速上手示例，包括大量示例与完整 recipe 的 cookbook。设计开源生态时希望是一个 AI-native 的机制：cookbook 是 coding agent 可以自己去读、自己去跑里面的例子、自己用它进行研究的；MinT 提供的 API 足够简洁且经过了大量测试，agent 确实可以在里面自己提交训练、评测筛选，然后进行研究。讲者展示了一个法律例子上 auto research 的轨迹：灰色点是 coding agent 基于 MinT 实验淘汰的候选方案，蓝色圈是保留的，折线是随时间变化的当前 SOTA，紫色是完整 benchmark 的结果；可以看到 coding agent 基于 MinT 自我迭代，整个指标不断上升，最后的版本既通过了 agent 优化的中间指标，也通过了最终完整的 benchmark。

从用户角度看，一次完整的 MinT 工作流就是六步：先选择一个基模，配置数据和 reward，提交训练，导出 adapter 获得一个 id，对它进行评测，最后上线；每一步都可以通过 API、甚至在线 UI 完成。若通过代码实现也很简单，讲者展示了 SFT 与 RL 两种常用范式的核心代码：第一段是创建客户端并指定基模与 LoRA 配置；第二段是 SFT 循环，只有两行——算一下梯度、进行一下优化器更新；第三段 RL 多一个 sample 步骤，用当前 LoRA 版本采样，拿到 reward 后指定损失函数进行策略更新。整个 SFT 加 RL 的流程都可以用一套统一的客户端 API 完成。

### 总结与 Q&A 边界

讲者总结三点：第一，MinT 的核心观点是用 LoRA adapter 作为核心对象，整个训练、评测、上线的循环都围绕 adapter，而不是完整的基模；第二，从 0.6B 模型一直支持到万亿参数模型，使用同一条路径，有百万级 LoRA 的 catalog 按需加载，可以保证整体加载效率，不需要为每一个 LoRA 复制基模；第三，已经在 GLM 5.1 的微调以及 GLM 5.2 的支持、用户端 agent 模型以及大量企业端场景中进行了实际验证。

Q&A 中讲者给出的几个坦白边界值得单独记下：

- 与 vLLM / SGLang 等不是竞争关系，更多是生态互补；开源仓库 vil-mint（字幕口径）底层基于 vLLM 提供的引擎，MinT 更多在系统层面把现有 infra 工作组合起来，根据 multi-LoRA 需求做改进。
- 与 Tinker 完全兼容，用户甚至可以直接 import Tinker 的客户端来使用 MinT 服务；对比优势一是第一个支持 GLM 5.1 与 GLM 5.2，二是进行了开源展示，大家能在一台机器上部署的小模型都不闭源，可以直接克隆开源代码自己部署，也可以在团队内部提供 multi-LoRA 服务。
- 「每一个用户一个 LoRA」最大的缺点还是在成本层面：实话说现在也没有完全做到真的在产品中给每一个用户训练一个 LoRA，成本还有非常大的提升空间；相比用 context 实现个性化，LoRA 里能记住的用户偏好以及真正能干预的风格、真正影响模型行为的程度肯定是训练到模型里更彻底，他们也有 LoRA as memory 的研究工作在对比。
- 训推一致是否必须实现精准的 bit-wise 对齐？答案是不需要，也不可能——训推至少基于现在这一套使用单独引擎、单独优化架构，不可能做到完全精确对齐；实际是带着一些训推不一致在训，先从机理上缓解一部分，对确实不可解决的训推不一致用 importance sampling 截断或丢弃一部分数据；采到大量数据其中有 80% token 可用，就是一个非常可用的训练系统。
- 基模更换后所有 LoRA 是否都需要重新训练？目前看简单答案是是的，基模更换以后所有 LoRA 基本需要重新训练；也可以用蒸馏等方法把旧有模型中的知识传递过来；基模权重变化时原有 LoRA 如何复用，仍是一个比较 active 的研究问题。
- 如何评估和管理僵尸 adapter 的存储与元数据维护成本、是否有自动化降级或归档机制？这涉及之后业务需求规模上来后是否需要给出第四级缓存的问题，可能还需要降级，把不需要的 adapter 放到真正冷的、成本更低的存储中。

## 可迁移

- 对 RL infra 工作的直接启发是把「权重交接量」当成一等公民：当基模常驻、交接对象从数百 GB 压到数百 MB 时，RL 的 rollout–update 循环每步的固定开销被数量级压低，这比优化单次 kernel 更先决定端到端吞吐。凡是训推分离的 RL 系统，都值得先算一笔「每步到底搬多少字节」的账。
- 训推一致性的工程分层值得照搬：能 replay 的离散决策（MoE routing，决策数小）就强制重放对齐；决策数大到不可 replay 的（DSA indexer），改用重要性采样式的降权/丢弃稳定梯度。先按「决策数量与可记录性」分诊，再选对齐手段，而不是一上来追求 bit-wise 对齐。
- 百万级 adapter 的管理本质是缓存问题而非存储问题：catalog 规模本身不是瓶颈（10 万级 warm 延迟基本不变），命中率与预热策略才是。可以把「热 / 温 / 冷」三级驻留与后台预热直接迁移到任何多租户 LoRA serving 的设计评审中。
- 训练侧多策略调度用时间维度而非空间维度：单 LoRA 已能打满 GPU 时，与其追求同卡并行，不如做分时切换填掉 rollout 等待的泡泡——千问三 4B 三个 GRPO 策略 51 分钟到 29 分钟、峰值显存不变，是这个取舍的现成证据。
