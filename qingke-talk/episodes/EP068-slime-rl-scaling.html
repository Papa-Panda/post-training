2一句话总结

这是一场「先讲为什么，再讲怎么做」的框架设计 talk：朱子霖从 PyTorch vs TensorFlow 的历史出发，论证 RL 框架的第一性问题不是 kernel 快慢，而是第一天就定死不能轻易更改的骨架与算法人力远多于 infra 人力时如何组织协作；slime 的答案是训练钉死 Megatron、生成钉死 SGLang 并全量透传两边参数，把 rollout 做成朝 OpenAI 兼容 server 打请求的 server-based 形态，框架自身只保留资源编排与数据搬运，从而以四个月、极少人力承接了智谱内部全部纯文本 RL 与 GLM-4.5 的三个 RL 阶段。

3核心

骨架先于性能：讲者对「框架在设计什么」的回答

讲者先把问题抽离：infra 是物理世界（硬件）与数学逻辑（算法）之间的桥，桥的第一要求是通（正确性），第二是畅（速度）；但这两件事主要由大规模实验验证与 kernel/通信专家决定，框架工程师真正的产出是另外两件：

  1. 定骨架。PyTorch 与 TensorFlow 之争的教训是：动态图 vs 静态图、向后兼容 vs 割裂升级，这些第一天的选择后面花多大力气都抹不平。「我们在设计框架的时候最最重要的一件事情，就是我们最开始定说这个框架是一个什么东西的时候，是要想的足够清楚的」（字幕 17:48–17:55）。
  2. 解决人的问题。RL 团队的人力结构是「一个团队里面有 30 个算法老师，而只有两个 infra」（字幕 26:17–26:21，讲者的量级示意）；o1 之后每人都有二三十个想试的实验，框架必须让算法同学的一次性实验代码直接跑起来、让社区贡献者愿意进来，同时复用成熟项目止损重复造轮子——讲者概括为开源节流。

由此他把训练框架史分成三个时代：table-top 时代（PyTorch/HuggingFace 式高自由度，借用杨振宁对高能物理的比喻）、pretrain-scaling 时代（Megatron 式极致正确性与全量优化，「不存在提前优化」）、RL-scaling 时代（o1 之后；实验仍然贵、正确性仍然命门，但算法与任务形态快速发散——GRPO/GSPO 等新算法、多模态、sandbox、agent 环境）。RL 框架的骨架必须同时继承前两个时代：Megatron 的正确性底盘 + PyTorch 时代的灵活性。

slime 的骨架：两个钉死、一个放开

  • 训练钉死 Megatron、生成钉死 SGLang，全参数透传。SGLang 的全部参数经 slime 原样传入、不做任何修改或过滤，SGLang 新增能力自动注册进来（字幕 33:37–33:50）；Megatron 侧则兼容各团队在 training 入口注册参数的魔改习惯，不侵入 Megatron 本体即可换版本或换内部魔改版（字幕 34:44–34:56）。理由是跟随上游的最佳工况：框架版本被掐死，两个引擎的持续优化红利就吃不到。
  • rollout 完全自定义 + server-based engine。数据生成开放为用户自定义函数：把 SGLang 当 OpenAI 兼容 server 起起来，生成逻辑就是往上打异步 HTTP 请求；多轮、工具调用与单轮在接口上没有区别。讲者明确反对 engine-based（在框架进程里嵌推理引擎、逐个对 generate 接口传参）的旧形态——接口变更即维护负担（字幕 35:20–37:29）。
  • 同地/分离、同步/异步只是资源排布。Ray 只做 GPU 资源分配与 rollout 数据搬运：两类排布共享同一套代码（字幕 37:30–38:45）。权重更新与 EP 通信不走 Ray——权重走 CUDA IPC / NCCL 直连，rollout 数据只传 token 与 loss mask，单点发给 Megatron 一侧再内部 broadcast，数据量小到 Ray 不会成为瓶颈（字幕 58:24–59:47、75:06–75:41）。这是对「Ray 口碑不好会不会是大坑」一问的正面回答。
  • 调试纪律：可只加载 rollout 或只加载训练，rollout 输出可逐条落盘，用固定数据单独验训练侧（字幕 39:04–39:28）。

这套骨架「涌现」出两个讲者事先没完全预期的能力：其一是纯异步 agent 方案——agent 环境完全在框架外自理，只向 SGLang 服务打请求并落盘轨迹，训练侧适时给服务发 pause、更新参数、再 continue（讲者称已给 SGLang 合入 pause/continue 类接口，字幕 98:15–98:23），环境多重、多复杂都不必改 RL 框架；其二是后训练全程统一——只用训练侧就是 SFT，只用生成侧加 SFT loss 就是 online rejection sampling，再接上评估，预训练 Megatron 的 checkpoint 可以一路顺到 SFT、RL 与线上 serving 而不换镜像不转格式（字幕 41:52–42:49）。

生产验证：四个月从零到 GLM-4.5

讲者自述 2025 年 3–4 月加入智谱后从零设计实现，约四个月内 slime 已承接智谱内部日常全部纯文本 RL 实验，并在几千到上万卡规模、GLM-4.5 这一 300 多 B 的 MoE 上做验证；刚发布的 GLM-4.5 35B 与 106B 均由 slime 训练，GLM-4.5 的三个 RL 阶段（通用 RLHF 类训练、reasoning/math/code 的 long-CoT 训练、agent/SWE 任务）全部跑在 slime 上（字幕 09:26–10:01）。他的验证观很明确：框架不能指望别人来吃螃蟹，要先有大规模落地场景再开源；且内外版本保持一致（仅模型未发布期内部封版），开源的意义就在内部实验与外部优化互相反哺。

Q&A 中最有信息量的几组判断

  • 为什么选 SGLang 而非 vLLM（字幕 51:22–55:56）：一是大 EP 场景下 MoE 推理性能优势，而 350B 级模型的 RL 推理是最大瓶颈；二是 SGLang 对 server-based 形态的支持更完善；三是国内社区活跃度与 PR 合入力。和上一条呼应：他不相信双后端抽象，「两个人做了完全不同的优化方案，RL 这边需要去给他们找一个交集，结果就是两边的最好优化都没有用上」。
  • 为什么不上 FSDP/DeepSpeed 后端（字幕 71:13–72:27 与 44:31–45:21）：短期内不做。写一个 FSDP 后端不难，难的是大规模正确性验证；内部没在用的后端一旦开源出去、出问题反而打破内外互哺。与其多后端，不如把 Megatron 的使用门槛降下来。
  • on/off-policy 的工程账（字幕 63:52–66:05）：纯 on-policy 在长上下文 MoE 上效率不可接受——生成很容易推到 64K/80K，但只有约 1% 的 sample 真正打满长度，MoE 每步又要访问几乎全部参数，等于只买了 HBM 带宽没买算力；「推理一步训一步」若能换成「推理一步训四步」，总时长可减半。拖尾问题用动态采样（过采样 + 全对/全错过滤）加先到先得凑满即停，配合 partial rollout（被截停的半成品下个迭代续推、复用已算部分，字幕 69:52–70:23）回收。
  • 数值一致性：训练前用训练引擎把 rollout 的 logprob 重算一遍，可保证每个训练步的「第一步 KL 严格等于零」，这是他们对训推不一致的验收线（字幕 95:06–95:57）。
  • 权重更新三通道（字幕 62:11–63:47）：同卡用 update-from-tensor（CUDA IPC 传显存指针）、跨卡用 update-from-distributed（NCCL 广播）、异构/跨集群用 update-from-disk（写共享盘、推理侧自行加载，慢但容错与解耦最好）。
  • 框架评价标准（答「NeMo RL 怎么样」，字幕 92:50–93:28）：看它有没有人吃过螃蟹（大规模验证）、能不能保证高性能、骨架是否想清楚——「一个一个滤一下，基本上就是我对一个框架整体感觉」。答「如何深入学习框架」时他推荐读 TensorFlow 1.x 的 C++ 代码与 PyTorch 的 Python 代码，带问题读、做笔记，并直言不太推荐用 AI 工具读代码做深入学习（字幕 79:41–80:48）。

下一步（讲授自述 + Q&A 补充）

短期：FP8 训练（复用预训练侧经验）、MTP/speculative decoding 进 rollout、降低 Megatron 门槛，以及他点名缺失的一件事——RL 框架之间需要一个像推理侧 R1 serving 基准那样可比的统一 benchmark，现在各家拿各自的设置对轰没有意义（字幕 45:25–46:17）。现状精度口径：训练 BF16 + 推理 FP8（GLM 训练中 rollout 已用 FP8 A8W8，字幕 76:49–77:05），理想是像 DeepSeek R1 那样训推统一 FP8；weight-only INT8/INT4 因每步都要做 calibration、开销太大暂不考虑（字幕 77:09–77:42）。长期：多模态 agent 环境变重后的资源利用、训练与推理异构硬件混布与跨集群、重环境下瓶颈不在 GPU 时的调度（字幕 46:18–48:35）。

5可迁移

  • 选框架的四问清单（可直接借用讲者的评价框架）：骨架第一天是否想清楚、有没有大规模场景吃过螃蟹、核心引擎是否保持在上游最佳工况（参数透传而非掐版本）、数据生成接口是否开放到「算法同学写个函数就能跑」。
  • 对 agentic RL infra 的直接启示：server-based 边界（OpenAI 兼容 API + 轨迹落盘 + pause/continue 更新）把「环境复杂度」挡在框架之外，这正是 agent 环境只会越来越重的方向上最省人力的切法；权重更新三通道（IPC/NCCL/disk）按容错需求分层也是现成菜单。
  • 调试纪律照抄：rollout-only / train-only 双模式 + rollout 全量落盘可复现；训推一致性用「第一步 KL 严格为零」做验收线，比事后对曲线便宜。
