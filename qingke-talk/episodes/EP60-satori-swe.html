2一句话总结

讲者针对「开源小模型做 SWE 落后闭源大模型」的差距指出：既有 test-time scaling 靠上百次并行采样刷分，采样效率太低——高分解在分布里是长尾。Satori-SWE 改用 evolutionary test-time scaling：先把前一轮中精选的候选 patch 塞回 prompt 当条件，让模型下一轮在此基础上修正，如此逐轮把生成分布推向高分区；为把这一「候选评估→改进」的迭代本事真正教会模型，训练走两段——先用 mutation SFT 教「如何从一个候选出发改到 oracle patch」，再用经 potential shaping 处理的 RL 把奖励稠密化、让每一轮都对「比上一轮更好」负责；推理时则可甩开 reward model 自行迭代，最终用约一半的样本量追平并超过重采样基线。

3核心

问题：小模型上 SWE，先撞上的是采样效率

SWE-bench 类任务的输入是 GitHub issue 描述 + 整个代码库，输出是一个能通过相关单元测试的 patch。讲者把管线拆成两种：agent 式（在终端环境里交互式查文件、写代码）与 agentless 式（先 retrieval 定位最可能出 bug 的文件，再把文件内容交给 editor 一次生成 patch）——本工作走后者，并把 retrieval 简化为「取一个或多个文件、内容全给 editor」。

差距的量级（字幕口径）：最好的开源模型在 SWE-bench 约 47 分，闭源模型配好架构可到约 70 分。而依赖闭源云端模型在生产中有代码数据泄露风险，所以要在本地/自有服务器上部署小一些的开源模型——差距必须有可落地的弥补办法。既有 test-time scaling 已有效果：先行工作（字幕作「SVIRO」）靠采样加 verifier 选择能把 33 分提到约 41 分，但代价是 160–500 次采样（字幕口径）。讲者指出 SWE 任务采样效率问题格外严重：其一，每个候选都要跑模型自生成的单元测试来挑选，而单个测试跑完需要几分钟甚至半小时；其二，整文件塞进上下文使单次推理本身就比数学任务长得多。

根因诊断：先用最简单的 SFT 教会模型做这个任务再大量采样，用 reward model 给结果打分，会看到高分结果在采样分布里只处在长尾——靠独立同分布采样翻到高分的概率很低。于是问题改写为：能否让模型逐轮把自己的生成分布往高分区推？

方法：Evolutionary Test-Time Scaling（ETS）

ETS 是 sequential scaling 与 parallel scaling 的混合：先并行生成 $N$ 个候选，选出 $K$ 个（字幕口径：首轮 25、次轮 25）放入下一轮的 conditional prompt，模型要分析已有候选的好坏并给出改进版；逐轮迭代，直到分布收敛到高分区。经典 SFT 直接套这个流程会失效：讲者实验里逐轮越来越差，效果远低于并行 scaling。

关键在于「改进型条件生成」这种能力要专门教。讲者构造 mutation 数据：用已训出的 SFT 模型在真实问题上先生成 patch candidate，把 candidate 与 problem statement 一起作为输入，thinking 内容是对每个 candidate 的成分分析（哪部分可借鉴、哪部分错了但有可取处），终点是 oracle patch——即「从一个具体候选出发，走到标准答案的一条路」。thinking 链的生成方式（Q&A 透露）：用 DeepSeek-V3 一类强模型，老实地把 oracle 答案也放进 prompt、让它「假装不知道答案」地写出分析过程，再用 oracle 与模型输出的 string matching 把对不上的坏数据（包括说一套给一套的「幻术」推理）过滤掉。mutation 数据与经典 SFT 数据一比一混合，训出 mutation SFT。效果（字幕口径）：第一轮迭代即可稳定优于前一轮；哪怕只用 5% 的数据（相比用全量数据的经典 SFT 模型），迭代曲线仍更好。

RL 阶段：甩开 reward model，并把最终奖励稠密化

mutation SFT 仍依赖一个外部装置：每轮都要先用 reward model 选出的 top-K 候选才能进入下一轮，这既让推理没法与 reward model 并行，也保留了额外的选择成本。能不能让模型直接随机取样、不经选择就进入下一轮条件？讲者实验里纯 SFT 模型做不到：迭代后分数直接掉很多、无改进。

于是上 RL（字幕多处作「IO/OO」）。朴素目标是只最大化最终一轮的 reward：

$$R_T$$

这里 ， $R_t$ ， 表示第 ， $t$ ， 轮候选经 reward model 打出的得分、 ， $T$ ， 为总轮数。问题是中间各轮的 reward 恒为零、信号太稀疏，且多轮串行采样使训练效率与实现难度都很高。讲者用 potential shaping 把目标重写成「每一轮都要比上一轮好」：塑形奖励定义为相邻轮得分的差分（字幕口径），

$$\tilde{R}_t = R_t - R_{t-1}$$

再叠加一项 format penalty：模型输出要能转成合法的 patch 文本格式（字幕作「GPATCH」），语法不合规就扣分。这样每轮生成都有直接的信用赋值。训练结果（字幕口径）：相比纯 mutation SFT 不再只是会迭代，而是迭代的每一轮单调更优、整体准确率也有明显提升。推理端则可以把 reward model 拿掉（最终全体样本生成完后仍可用 reward model + 单元测试做一次总选择）。

实验：样本效率是主要主张

与先行工作的对标（Q&A 口径）：对方用 70B 模型、500 步采样做到 41 分；Satori-SWE 用 50 步采样就做到 41.6 分；训练数据约 30K 条样本，比对方少。收敛图上（字幕口径），ETS 用约一半的样本量就达到与 unit-test verifier 选择相当的收敛结果。最后在 SWE-bench Verified 上，用更少的样本量做到了当时社区内比较高的结果（具体数值字幕未逐项报出，本文不臆写）。

规模化边界同样来自 Q&A：硬件为 128 张 H100、在 32B 模型上做实验。讲者试过 7B（Qwen2.5-Coder-7B 方向）——SFT 之后再 RL 效果始终不好，zero-shot RL 的 7B「学不动、乱生成」；32B 的 zero-shot RL 也能涨，但幅度不大，后来改用 SFT 做基座再接 RL 才顺。也就是说这套迭代本事对基座能力有门槛。

另一个坦白的工程限制：RL 阶段没法真的在 docker 里跑单元测试拿真实奖励（环境代价太高），reward 实际主要来自 reward model，辅以 string matching 兜底（让合成的数据更稳定，不加 string matching 模型常说错话）；讲者判断「换成 reward 模型在其它场景也一样可用」，但其他场景尚未实测。代码当时还在整理（数据与模型已开源，字幕口径）。

5可迁移

  • 「逐轮把分布推向高分区」是 test-time scaling 的第三条路，值得和 best-of-N 对照着想：当 verifier 很贵（必须跑完整单元测试）时，独立采样再挑选的边际收益会迅速变差；让模型看见前一轮的候选并针对性修正，等于把挑选成本的一部分转嫁成了条件生成能力。若你有类似「验证贵、生成相对便宜」的任务，可以先在小规模验证：经典 SFT 之后直接迭代会不会变差（讲者的负结果是很好的基线提醒）。
  • mutation 数据的构造配方可迁移：让模型学会「从老师/自己的中间产出出发、分析可借鉴成分、最后落到 oracle」，这条「候选→分析→答案」的轨迹比直接答案轨迹更能教出迭代改进；thinking 的防幻术过滤（把 oracle 塞进 prompt 让强模型反写理由，再用 string matching 把不自洽的剔除）也是实用的廉价数据清洗手段。
  • RL 稀疏奖励下先做差分塑形：当任务目标只能定义在最终结果上、但任何中间结果都有可打分的代理（如 reward model），把奖励改成相邻轮的差分能把信用分配稠密化；同时把「格式合法」单独做成 penalty 项，避免把它和质量信号搅在一起。
  • 爬坡曲线用法：讲者用「每轮是否单调更优」而不是只看终点来评判迭代能力，这对自改进类系统是个好习惯——终点分相同，单调迭代的能力结构完全是另一回事。
