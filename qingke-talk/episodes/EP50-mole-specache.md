## 一句话总结

讲者从端侧存储层次出发，把优化目标定为「下层存储承担大部分占用、但每步只读回一小部分」加「读与算可并行」，并据此给出两篇互补工作：MoLE 通过把专家输入改为 embedding token、把专家重参数化为下层存储中的查找表，做到全专家激活又无需把专家权重搬进显存（每 token 传输量较专家卸载降千倍以上）；SpeCache 则对 KV cache 做「全量卸载 + 显存内 1-bit 估计副本 + 用投机 token 提前一步预取 top-k 16-bit KV」的稀疏预取，以约 5% 延迟增加换来接近 16-bit 的长上下文推理质量。

## 核心

### 背景：端侧部署瓶颈不在计算，而在内存与存储层次

讲者把端侧部署的动机归结为三点：算力成本（自部署 DeepSeek V3/R1 量级至少 8 张 H20、显卡成本 10 万美元以上，而个人只能部署约 7B 的小模型）、离线访问（手机 AI 助手在未联网时也要可用）、数据安全（隐私与内部数据不能走外部 API）。但 LLM 解码阶段本质是 **memory-bound**：每步只产生一个输出 token，计算量不大，耗时主要消耗在参数与 KV Cache 的读写上。端侧的麻烦在于存储层次——显存/运行内存容量小且贵、磁盘容量大但带宽慢；问题就变成如何让下层承担主要「存放责任」，同时让推理过程只「读取一小部分」。

由此讲者把端侧存储优化拆成两个通用条件：(1) **稀疏利用**——被卸载到下层的内容每次只用其中很小一部分，使传输量可控；(2) **提前感知**——提前知道下一步需要读哪些内容，把读取时机提前与计算并行。下面两篇工作各自覆盖一条（或两条）约束。

### 问题分析：参数与 KV Cache 是两处独立的大头

讲者点名两处占用来源：模型参数（近期 MoE 把总参数量推大、激活参数量却很小，于是「存不下」比「算不动」更难受）与 KV Cache（长序列时可超过模型本身，如 Llama 2-7B 在输出 1000、batch 64 时超过 8B）。后续两篇工作正是一篇管参数、一篇管 KV Cache。

### MoLE：把专家从「计算的专家」改成「查找的专家」

常规解法有两条路，但都有硬伤：专家卸载（专家全留 CPU RAM/ROM，运行时按需加载）与专家裁剪/融合。卸载结果虽与原模型完全一致，但每次新 token（或 batch 中不同 token）需要不同专家时，先要把整批专家矩阵搬进显存，批量越大搬得越重；裁剪在降到 50% 以下明显掉点。

MoLE 的核心改动来自一个观察：embedding token 天生离散、有限（几十K 个），训练结束即固定。讲者把路由专家的**输入**从上一层输出改为直接来自 embedding token；这样在训练结束后，可对每个 embedding token × 每个路由专家预计算输出，形成查找表；推理时每个 token 按 token id 直接从表中取结果、再按路由权重加权（route 的输入仍是上一层输出），专家本身不再做任何矩阵计算。

由此带来一组设计红利：专家变表后不需要稀疏激活，推理时**全专家激活**，整个模型可导、不再需要 load balance / z loss；传输量从「专家矩阵」变为「专家数量个结果向量」，即每 token 传输量骤降。代价是：embedding token 相对于中间层特征丢失了上下文信息。讲者靠共享 FFN + attention 本身承担上下文相关的信息、在设计上把「查表专家」视为 dense 模型外挂的下层存储表来补偿。

可扩展性讨论中有两条经验值得记：增大单个专家隐藏维度（768 → 3072 字幕口径）有用但存在天花板——推理形态的参数量会把性能「蚌住」（字幕口径，即被固定住/卡住），无法靠无限放大专家获取 free lunch；而扩大专家数量能给出更干净的 scaling law，但查找表大小与传输量都随专家数线性增长。架构消融拆解了每一步代价：全激活先放大激活参数量并带来明显提升；10 个路由专家重排为「1 共享 + 4 路由」时略降；把专家输入换成 embedding 的**一步造成最大性能下降**；重参数化为查找表一步计算逻辑不变、但把推理激活参数量压到最低；最终整体性能大致持平 dense / MoE。

速度实验（V100、卸载到 CPU RAM）显示 MoLE 的额外传输可几乎忽略：其一传输量很小；其二 token id 一旦确定、不待后续计算也能提前开始加载查找结果，与后续计算完全并行。一个未被展开的备份细节是查找表本身还能在训练后做 NF4/NF3 量化（QLoRA 的 NormalFloat），讲者报告 3-bit 仍能保持与 16-bit 相近的性能。
