## 一句话总结

把一家虚拟软件公司装进 LLM 里：按瀑布模型切「交流链」，每节链上由 instructor/assistant 两角色对话完成子目标，靠角色化 prompt、记忆流、自反思解决跑题与幻觉；再往上加一层 Co-Learning（共同彩排—捷径经验—共同推理）让智能体跨任务积累经验、走捷径。讲者自己的结论很克制：ChatDev 当时把代码写对的概率约 50%，幻觉仍是这个方向最大的问题。

## 核心

### 1. 背景/问题：为什么要多智能体

讲者的出发点是知识分布：不同 LLM 训练出的知识不一样，群体协作可以把不同模型的知识做汇总与优势互补，而语言（自然语言与编程语言）是承载各类知识、搭建协作桥梁的天然媒介。复杂任务（如「开发一个五子棋游戏」）交给这样一个群体，用类似生产流水线的方式完成。

讲者把多智能体构建拆成两个层次的关键问题：

- **智能个体**：需要在基座模型之外补记忆、规划、工具、语言交互能力（复杂场景还要视觉感知）；
- **智能群体**：需要共同目标、组织结构（谁是谁的上级、合作还是竞争）、以及在静态组织结构之上的动态路由——组织是静态的图，路由是在图上做序列决策。

### 2. 方法/设计：交流链 + 三个节点机制 + Co-Learning

**ChatDev 的组织形式是「交流链」**：按瀑布模型把软件开发拆成设计、编码、测试、文档四个阶段；多智能体交互被简化为两两交互（如 CTO 先与程序员交互定方案，程序员再与设计师交互）。每节链上设两个角色：`instructor`（指导者，抛意见、布置任务，像教师）和 `assistant`（助理员，生成当前节点的解决方案，像学生），多轮对话共同定下子目标（如软件形态、用什么编程语言），方案由外层框架从对话中抽出。

每节链的节点靠三个机制跑稳：

1. **角色化**：用 prompt engineering 把大模型复刻成 CEO/CTO/程序员/设计师/评审/测试员等职能角色；讲者举例：把角色定义成细致的 Python 程序员，它就更容易发现 Python 的 bug（也可以用 fine-tune 注入角色，不限于 prompt）。
2. **记忆流**：每轮交互把前文上下文完整喂回，智能体感知全部聊天过程再决策（CEO 问「用什么语言」、CTO 答 Java 太复杂、最终定 Python，这类共识靠上下文维持）。
3. **自反思**：agent 不听话时会一直礼貌问好或 say goodbye；解法是把整段对话喂给 assistant，让它自己总结「到底达成了什么结论」，用类似文本摘要的机制抽取结论，截断跑题。

**幻觉缓解靠「角色翻转」**：不让测试员直接命令程序员改代码，而是程序员先提问、测试员给定位与修改意见，意见再喂回程序员改代码——本质是把改 bug 变成一条 CoT：先定位、再推理、再执行。讲者特意把词从「消除」改成「缓解」：幻觉不太可能百分之百消除。

**演化层是 Co-Learning（经验式共学习）**，受人类学习（彩排—积累教训—迁移）启发，与协作层正交：

- **共同彩排**：在历史任务上重走执行轨迹。一次任务执行被组织成「任务执行轨迹图」：instruction 存在边上，solution（代码版本）存在节点上，状态从空版本一步步演进。
- **捷径式经验**：经验被显式定义为从 $V_1$ 跳到 $V_4$ ，乃至从 $V_0$ 一步到 $V_5$ 的捷径，把中间没必要的尝试替换掉。存储分工是共学习的要害：instructor 存「看到什么 solution 就该给什么指导」（key 是节点），assistant 存「拿到什么指导就生成什么 solution」（key 是边/instruction）——单方记忆不行，节点和边必须共同记住。
- **共同推理**：新任务推理时，instructor 先查自己的记忆库让指导更精确，assistant 再查自己的记忆库生成更好的解，两边都被经验增强。

### 3. 实验/实战

- **自主性观察**：设计与编码阶段智能体全程无人类参与，自主讨论目标用户、数据管理、UI 与可配置化；评审/测试多轮迭代中，软件版本会从 error 逐渐转向 success，编译成功率逐步提高；但也有代码在已编译成功后又被改错的情况，所以做法上可在编译成功时直接停止当前轮交互。
- **规模的坦白**：演示 case 是词典、名片生成器这类小软件；讲者明确说自主开发软件的类型与规模还比较小，中/大规模是未来目标，并列出四件事——写对（无 bug）、写快、写长（模块化层次分解，目前还没有对应工作）、写齐（与需求对齐），期待一到五年内做成。
- **现状数字（Q&A 字幕口径）**：ChatDev 写对代码的概率大概 50% 左右。

### 4. 结论/观点（事实 vs 观点分开标注）

- 讲者的核心判断（观点）：LLM agent 方向起来还不到一年，多智能体系统更只有约半年，成熟度很低、研究空白很大；未来最需要解决的问题是幻觉——生成式模型逐 token 采样会采到低频 token，这是幻觉的本质来源。
- 工程事实（Q&A 确认）：review 是静态 debug（靠模型看代码找错，如没 import 的模块），test 是动态 debug（借编译器）；框架支持把整条链配置化改造成别的领域（如新闻编辑室：换角色与子步骤即可）；基座经 API 调用，本地跑 Python 即可，换本地开源模型官方未适配（社区用 LiteLLM 接入）；Linux/Mac/Windows 均可直接跑，担心生成代码安全性可开 Docker 模式；讲者称目前没发现基座模型故意写恶意代码。

## 可迁移

- **组织结构静态、路由动态**这对概念可以直接搬到多 agent 编排系统（包括 agent harness）：先定死组织图与职责边界，再在图上做动态调度决策，比边跑边改组织稳定得多。
- **「经验 = 从中间版本直达终版的捷径」**是个很实用的经验存储形式：对 coding agent 来说，存「什么问题给什么修复」与「什么指导生成什么代码」的双边键值对，比存原始轨迹更省、迁移更稳——和经验回放里存压缩转移而非全轨迹同理。
- **自反思截断跑题**：给长对话加一个周期性的「总结当前结论」步骤，是低成本防跑偏手段，对长程 rollout 的 prompt 设计也适用。
