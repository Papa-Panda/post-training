2一句话总结

四位嘉宾对 RL Infra 的判断高度收敛：单轮、GPU-heavy 的 RLVR 阶段已被攻克，下一程的主战场是 agent RL 带来的完全异步流水线、CPU/异构集群与环境接口标准化；但真正的开放问题不在框架而在 reward——数学/代码之外的 reward 如何定义、如何不被 hack、以及 LLM-as-judge 的系统成本，仍没有收敛答案，学术界的机会恰在于此：用小规模实验产出可 scale 的 insight，再由工业界与开源社区完成规模化验证。

3核心

开场：RL Infra 接下来最重要的 feature 是什么

主持人张开元先抛开场题：从 hybrid engine 到异步流水线，未来最重要的方向是什么。三位工业界嘉宾的回答各有侧重，但都指向 agent RL。

邵凡（verl / agent RL 侧）：verl 最初从 RLVR 迭代到 agent RL，后续会继续在 agent RL 上发力，工程重点是完全异步——rollout 阶段加速、训练加速、以及把整个训练过程完全异步化。他判断这会是后续主流。

张涵（阶跃星辰侧）：他预判一个 paradigm shift——单轮、GPU-heavy 的任务已被攻克，现在观察到的现象是 CPU burden 越来越重。未来可能是混合集群训练：一侧是更专门化的 CPU 集群（要考虑 memory 与 CPU 本身），尤其服务于 software engineering 这类能创造价值的下游任务，甚至硬件构成都会改动；另一侧是 GPU 集群。两种集群之间怎么互联（networking）、interface 怎么设计、如何异步获取一个很慢的 software-engineering 任务的结果，会是系统方向下一批热门问题。

方家瑞（字节/火山侧）：他补充两条。第一就是 agent：更多工具调用，SWE-bench 这类任务对开源仍很难，因为它涉及 2000 多个 image 的切换，再加上未来的 computer use、打游戏等，都会放大非 GPU 负载。第二是 scale out：开源实验现在多是 32B、128 卡，顶多 1000 卡；企业级场景关注的是上百 B 的 MoE 怎么 scale 到万卡、能不能带来模型效果的质变——他认为这对开源框架尤其重要。

主持人小结为三点：agent、异构混合计算、scale up；并顺势引出下一个问题——阿里 GSPO 正是在几百 B MoE 训练中才暴露的问题，那么高校学生在大规模 RL 由工业界主导的时代能做什么。

学术界在 RL 时代的位置：insight 的供给方

雨辰（高校博士生代表）：学术界的任务是给业界提供 insight。业界更 focus 在具体任务与 KPI 上，企业算力要分成「完成 KPI 的算力」和「做创新的算力」，普通公司在创新算力上投入有限（他明确说不知道字节的投入口径）。高校能做的是在小场景上给出可 scale 的创新 insight，让业界在 scale 的场景下去验证和放大——关键是方法本身要 scalable。

工业界三位对此都表示认同，并给出各自的承接机制：

  • 方家瑞：实验室卡少没关系，如果能提出有 insight 的想法、后面需要 scale，企业有很多合作机会。他以 verl 社区为例：他们会主动找 promising 的论文合作、提供算力帮做验证，前提是成果能贡献进 verl 的 recipe 里；「把东西做 work、并且让社区看见」，算力问题企业愿意出资源帮忙。
  • 另一位工业界嘉宾（字幕未点名，按对话顺序在方家瑞之后发言）：从框架角度看，实验室研究规模小，但只要在同一套框架上做出效果、被大家看见，自然会有人在更大规模上替你做实验验证——所以框架层面的良好支持本身就是学术成果被放大的通道。
  • 张涵：他点出资源差带来的结构性后果——学术界拿到 feedback、产生 insight 的周期比企业内部慢一到两个月，这件事目前不可逆转，只能依赖 Seed 等企业把自己的 insight 开源出来。但他随即给出乐观判断：recipe 正在收敛（今年早些时候大家都在提「second half」），接下来是到具体下游「开花结果」的阶段，学术界在这方面的活力反而更充沛，因为企业内部各司其职、迸发不出那么多火花。模型变强本身也是红利：很多以前做不了的事，随着 Claude / GPT-5 一代模型把成功率从 60% 推到 90%，突然就变得可做了——学术界可以乘着能力红利做下游的新问题。
  • 席间一位嘉宾（字幕未点名）补充：自己给 verl 提了好几千行 PR——给开源框架提 PR 是学生被看见、进入合作的直接路径。

主持人总结：学校同学做好有 insight 的工作，企业会自己找上门；积极给开源框架提 PR；以及去做更下游的任务。

需要一套统一的 agent RL 环境接口吗

主持人把问题类比 MCP：MCP 统一了工具调用，那 RL 是否也需要一套统一的环境接口，让不同框架间可以迁移复用（类比早期 OpenAI Gym，但 Gym 已太早期）。

  • 邵凡：verl 做 agent RL 的设计尽量贴近传统 RL 范式，ENV 接口保持 Gym 的 API 设计。他认为需要一套统一标准或范式，但具体业务场景未必那么标准：比如基于 Gym 构建的环境，最近社区有些 agent RL 工作需要「回退状态」的能力，传统接口实现不了，需要针对 agent 场景做特殊适配。他提到开源社区已有统一环境接口的工作，比如 GEM，感觉不错。
  • 雨辰：他坚定认为需要。不同环境会带来很细微的差别；奖励来自环境，哪怕不是 agent 场景、只是数学场景，verifier 的不同都会带来很大差异。如果要在统一 benchmark 上验证方法、让奖励更精准，统一标准挺必须——不是所有任务都像数学那样好验证，「差一点好像也还行」的任务尤其需要。
  • 张涵：他给出不同的思考方向，并明确说自己没有结论。MCP 为什么能被大家接受？需要统一接口是肯定的，但「谁来提这一套接口、能被大家广泛接受」才是更重要的事——这取决于行业影响力、技术能力与对社区的负责程度，可能不是算法或 CS 能回答的问题，而是社会学或经济学问题。如果国内要有人提，他希望是 verl 这边提出一个大家都完全接受的标准。
  • 方家瑞：他把场景分两种。一种是雨辰这类学生重点攻克的任务（SWE-bench、code sandbox），代码、数学是最好的两类 RL 任务，社区很快会有统一的环境乃至接口，大家重点做这几类。另一种是企业内部大量内部环境与工具，就像 MCP 一样没有动力统一（他举例：不会有微信朋友圈 MCP 这种东西），垂直场景一时半会很难统一；但标准任务应该会有人做。他还交代了 verl 的分工背景：verl 发起方主要是训练团队，他所在的火山 ToB 侧反而能给 verl 提供推理、MCP 支持等方面的输入。

这个问题没有结论，主持人定性为开放性问题，转入现场自由提问。

现场问答一：框架内幕与字节的 RL 规模

问张涵（阶跃星辰内部框架 vs 开源框架的关系）：提问者问阶跃当天挂出的 StreamRL 与 Stage Fusion 两篇工作用的强化框架（内部研发、训练部分在 Megatron 上魔改）与他维护的开源框架是什么关系。张涵答：「是没有关系的关系。」内部生产具体怎么实现保密，但肯定比 verl 快很多；开源框架主要是一个 interface，采用的 backend 都是开源 backend，从开源 backend 汲取养分，所以接口基于开源的框架大概率比企业内部专用框架慢。被追问开源框架在阶跃内部的定位，他给出「two-stack 健康论」：企业有一套生产框架、一套科研/开源框架是比较健康的格式——一方面快速接受开源社区的 input，另一方面用更快捷的方式做 idea 验证。

问方家瑞（字节 RL 的卡规模与数据规模）：提问者引 Grok 的例子——预训练与 RL 算力投入已基本打平（一半算力在 RL）。方家瑞先声明字节太大、他不可能有全局信息，但给出他的采样点：现在跑 DeepSeek 的 RL，6 月份时 512 张 H20 才能跑起来；671B 这种任务如果企业客户真要微调，最少要给 1000 卡的 budget。上半年大家（不止字节、阿里等头部，也包括腰部和中小企业）基本用开源框架玩 32B、7B/32B；下半年不可避免都会上大模型做 RL 生产，671B 或 235B 这种至少是 512 卡或 1024 卡起。他判断这是比较 general 的情况。

现场问答二：百 B 级 MoE 的 RL 支持难在哪

提问者指出：开源框架里真正能跑百 B、235B 起步并能复现的没几个（verl 与 slime 接近，slime 的 GLM-4.5 是 300 多 B），问 verl 做百 B 以上 MoE 的难点与踩过的坑。

方家瑞给出三段经验：

  1. loss 曲线对齐最耗时。verl 当时定位就是重点做大模型；第一难是 loss 曲线要能对上——3 月到 6 月一直在跟 Megatron 对齐，因为只有小规模时 Megatron 与 FSDP 能对上，scale 起来才可信；为了修 Megatron 的一些 bug 花了很长时间，是跟 NVIDIA、Amazon 的人一起合作做的。
  2. 性能爬坡未完成。现在 MFU 还不是很高（字幕口径：H20 上最新数据才 0.2 左右量级；正常预训练 MFU 应在六七十的量级——此处字幕数字口径粗略，见关键数字表注）。速度分两方面：rollout 速度看引擎（大家做得都挺好），更重要的是减少 GPU 等待时间，这正是各种 async 优化的价值；trainer 速度就看 MFU。
  3. 靠社区把大模型做稳定。随着越来越多人用大模型，verl 目前关注的重点是借社区力量把这套东西做稳定。

追问环节澄清了两个细节：

  • rollout 后 DP 间负载均衡：方家瑞认为这跟社区面临的挑战一样，但 roadmap 已基本收敛——要么 split、加上 AReaL 那种异步、控制 off-policy 程度，verl 基本都具备了；欠缺的是在生产环境真正用这套跑起来，以及 off-policy 怎么收敛这类算法问题值得研究。工程方案上各家框架已收敛到相似路线。（席间补充：训练侧因为序列都已 pack 到定长，不存在变长带来的 DP 不均衡。）
  • 671B 的精度/loss 怎么对：方家瑞答，小规模上 Megatron 精度对得差不多了，就基本认为 scale 起来没问题、曲线能正常收敛即可；那个规模 FSDP 也没有参照了。

MoE 相比 dense 的额外挑战（另一位提问者）：方家瑞认为这不是 RL 框架的问题，底层训推框架已解决——负载不均训练侧有 load balance、推理侧有 LB-DP 等，RL 直接复用。邵凡（按对话顺序补充）指出 MoE 下 log-prob 的计算精度需要特别考虑。张涵则借这个问题表达了他的保留看法：他没遇到过 GRPO 训崩，怀疑很多「挂掉」本质是目标函数的问题——比如 token-level 的除法在 off-policy 稍大时就炸，GSPO 出来后直接去掉 routing replay 也能成功，sequence-level 会稳定很多；他倾向于认为算法 recipe 收敛后，MoE 不会有那么多特殊 detail，因为它无非是 forward 和 backward，推理能稳定、训练大概率也能稳定。

现场问答三：数学与代码之外，reward 怎么做

这是全场分歧最大、也最开放的一段。提问者问 agent / deep research 这类开放任务的 reward 未来怎么做。

  • 邵凡先坦承这更像业务问题，他主要做框架设计与优化，没有太多经验，请算法同学解答。
  • 雨辰给出最明确的立场：search 这类任务还是要人去设计一套精密的构造——只用 outcome reward 会有 rubric 匹配的问题，想用 process reward 就要设计好「到达某个 golden webpage 给 reward」这类规则。他反对依赖 LLM 合成 reward：任何 synthetic 的 reward 最终都一定会被 hack，合成任务在真实操作时极易被 hack 恰恰因为 LLM 本身就容易被 hack。要做 scalable 的训练，就必须精细设计每一个问题——想要多精细的 reward，就得投入多精细的人力去标。
  • 张涵：没有 reward function 就搞 reward model，手段未完全收敛但思路已达成一致（要么 reward model、要么 reward function，中间还有 design 空间）。他用教育举例：评价一个老师是不是好老师，就是这个问题的具体形态，希望能给大家一些 spark。他明确表示这部分有他自己的 research idea 但没时间做，欢迎 intern 来找他。
  • 方家瑞：他自认系统出身，但同意 reward 是整个问题最核心的东西——引尧舜禹（字幕口径，人名以公开资料为准）的文章：能定义好 reward，问题基本就解了，大家要先学会提问。他给出采样点：他们最近的 CoLab（字幕口径）项目用 LLM 做 judge 来做 reward；rule-based 大家已玩得比较转，下一步是 LLM-as-judge。但从系统角度挑战很大：采样瞬间会有大量请求同时调 LLM 做 reward，对 LLM 的瞬时压力非常大，这块从系统角度值得做。
  • 邵凡顺着系统角度补充量级感：agentic 场景下，若 rollout 1024 条轨迹、用 1024 个环境并行，就会同时有 1024 个并发请求打到 reward LLM，对 reward 系统挑战非常大；现在的解决手段是部署远程 reward server，或在框架内部拉起 reward server 的 vLLM 实例，都需要专门考虑。

后续追问把 reward 的粒度问题展开：

  • 提问者问 agent 任务现在多以「多轮交互后最终是否完成任务」作 reward，粒度太粗，能否做到每一轮的细粒度监督。邵凡答：RL 设置里每个 step 本应返回 reward，现在 LLM RL 的普遍做法还是用整个 episode 的 reward 学习；已有一些工作基于 step 构造训练样本、按 episode reward 分配每个 step 的奖励，具体效果需要各自实验。
  • 雨辰重申他的立场并收紧表述：要多精细的 feedback，就得人为设计多复杂的规则去做这件事；他是坚定的 reward function 支持者——可以给 LLM 精密规则让它 follow instruction，但让它直接做价值判断很难、目前不 scalable。两条路：要么像他们组之前的 implicit PRM 那样「算出来」一个 process reward，要么真的用很多 golden label 去「标出来」，且标注者的 diversity 要保证；一旦让同一个东西既生成又打分，就真的很容易被 hack。

另一位提问者补充了第三条路的观察：用模型生成 rule 的范围、让 LLM 基于预定义规则做基于规则的 reward（并提到浙大同行有文章可参考）；但部署 reward model 又会带来 infra 挑战。

现场问答四：去中心化 RL 会成为主流吗

提问者问：前面有分享提到去中心化结构训 RL，大厂不缺卡的状态下，去中心化会不会在产业落地（像 SFT 那样规模化）时成为主流，还是继续「豪」的路线。

  • 张涵明确不看好（针对多方参与式的去中心化）：去中心化就要考虑拜占庭问题——参与方里有没有恶意方、给的 gradient 是不是错的。这跟当前主流的效率、经济性问题是两个垂直的问题。他最担心的激励问题是：真做了去中心化 RL，很可能有人拿你的 rollout 算力去挖矿，几个「老鼠屎」就能搅浑整锅汤，经济学上没有 incentive。除非是非区块链式、默认大家都是善良人的设定，但从系统角度看一定会有坏人，不能保证 50% 以上是好人，这件事就成不了。他同时给出他更看好的替代方向：异构的 disaggregation——rollout 放在更适合 rollout 的机器（如 H20）上、训练放在更好的机器上，把两边分开；agent environment 对 CPU 消耗更大，需要更好的部署，本质是用适合的机器做适合的事。
  • 方家瑞基本同意，并把问题拆成两种：一种是很多人一起完成一个任务的去中心化共识，已被验证无法形成大规模共识；另一种是把 RL 流程的一部分拿出来放到本地或安全的地方做，比如自己定义 reward function、本地执行 reward——这种需求是真实存在的，未来很快会有 MaaS 或云产品形态（像 OpenAI 已支持的 fine-tuning API：可以自己定义 reward function、自己定义 agent loop 调工具）。他判断各家都会开放这种形态。

现场问答五：LLM 做 reward 的系统架构怎么设计

清华的提问者从系统角度追问：用 LLM 做 reward 负载很高，实际生产中是专门有一个集群负责、怎么 manage 才能把 throughput 做高；而且 reward model 本身是否也要训练更新（像 critic 一样），会不会变成两个 RL 集群「左脚踩右脚」还互相 hack。

  • 邵凡（系统实现侧）：最初想法是直接弄一个 remote 的 LLM 在线服务请求，但反馈是太慢、扛不住这么大的 QPS，或者要投入更多资源。现在做得比较多的做法是在 rollout 内部起一套 reward server（跟 actor 类似，只是 不需要更新参数），底层用 vLLM/SGLang 自带 continuous batching，单独分一些卡只在 rollout 时给 reward 用，分多少卡按训练配置来平衡资源；remote server 的做法也有。关于 reward model 是否需要更新：他目前没遇到这样的 case，应该不需要更新。
  • 雨辰（算法侧）：reward model 永远不是 golden reward、永远会被 hack，哪怕只是跟一个简单的人为 ground truth 对比，这也是 LLM 做价值判断的大问题。他顺势介绍他们组的 implicit PRM：普通 LLM 做 reward 要部署后起 server，而 implicit PRM 不需要预先训练，它跟 policy 一起动态 update，且不需要 rollout、不需要 query 它输出，只需要做一次 forward 拿 log-prob——他认为「算出来」可能比「部署一个 judge」更科学，否则 LLM-as-judge 目前在实现与效果上都没有那么好。
  • 张涵（系统设计侧）：这件事是系统设计避不开的问题——慢就是慢，那就只能在 CS 角度想办法 overlap 掉开销；如果验证过确实有 gain，就应该付这个代价，代价就是要有一部分额外的推理集群，于是课题变成两个集群怎么配合、不要互相 idle，就是各种 pipelining / overlap，大家都很熟悉。他接着给出一个「大逆不道」的观点：显卡还有摩尔定律顶着，他不太担心 scale up；他真正担心的是 data 的墙——算法、算力的墙马上就没了（比如 B 系列卡出来后，一个 8 卡机器就能做现在需要一个集群做的事），但数据训着训着没了，entropy 不降，你又没那么多数据可加，这个更头疼（他自承这跟 CS 关系不大、有点岔开话题）。
  • 方家瑞补充云上算账的细节：用公有云 API 调 judge 是最省的（云厂商把供给都 pooling 好了），但他们算过——训练时有 TPM（token per minute）的概念，公有云保障包一分钟能给到的量级（字幕口径：10 万到百万量级，口径粗略）顶不住批量 1024 路并发 judge 的流量，从系统上比较难做。他判断这个方法目前还是有缺陷。

收尾：RL 与 AGI 的关系

主持人把最后一个问题留给 AGI：傅伟（字幕口径）在前面分享里画过坐标轴——AlphaGo 走的是采样次数极多（mini 级别）超过人类的路线，现在的 RL 也在不断增加采样次数，最终能不能达到 AGI/ASI。

  • 邵凡：他最近看 agent RL 的工作比较多，他的观点是 agent RL 是通向 AGI 的必经之路——agent 与环境（现实或其它环境）交互、积攒经验、通过经验提升自己，他觉得是比较合理的路径。
  • 雨辰（紧接发言，字幕未点名，按对话顺序）：RL 本来就有 self-evolve 的感觉，RL 肯定是实现 AGI 的必经之路、可能是达到 AGI 之前最重要的技术；它不断探索世界、获取反馈，跟人学习的方式很像，是一个很美妙的东西，不断采样、搜索、自进化。Agent 是加速 ASI/AGI 的必经之路，但更重要的是跟什么样的环境交互、用什么算法让它一直保持 explore。
  • 张涵：他的回答最简短也最激进——「AGI 既然已经到了，所以没什么可以评价的。」只要给他定义好 task，它就能学好、学上去；他自嘲现在考什么试都考不赢 AI（现场玩笑：把北大校规校纪输进 context、train 几下就好了）。他说自己做过一些小实验后对 AI 的能力潜力彻底改观：只要数据管够，什么都能学到百分之百，literally，7B 模型就能做到。所以问题在于下游——下游定义好任务、需要什么样的模型，训一训就有了；「这个时代很幸福」。
  • 方家瑞收尾：他 22 年做大模型时还不是所有人都愿意做，23 年最流行的话是「你信仰 AGI 吗」，信仰 AGI 才能来做大模型；但 23 年 RL 还不是主流方向（那时是 pretrain 的时代），信仰 AGI 与信不信仰 RL 当时还是两件事。从现在的共识看，在座各位应该都信仰 RL 了——至少在数学、代码场景能实打实看到超出人类的能力；但离 AGI 可能还得有几轮小的信仰改变。

主持人总结：不管能不能到达 AGI，现在 RL 就是最重要的事。

5可迁移

  • 给 RL infra 排优先级时，先看负载构成而不是先看卡数：张涵与方家瑞不约而同指出 agent RL 的新增成本主要在 CPU/环境侧（SWE-bench 的 2000 多个 image 切换、computer use、工具调用），GPU 集群与 CPU 集群的配比、互联与 interface 设计，应作为与 hybrid engine、异步流水线同级的基础设施议题，而不是等 GPU 侧优化完再补。
  • 开源框架的「学术放大器」用法：方家瑞与另一位嘉宾给出的路径对资源有限的团队直接可用——在同一套开源框架（如 verl）里把方法做 work、贡献进 recipe / 提 PR，成果被社区看见后，scale 验证可能由企业以算力合作形式完成；选题时按雨辰的标准自我检查：这个 insight 在小规模成立后，是否 scalable。
  • reward 设计先于 reward 部署：本场最可迁移的共识来自雨辰与张涵的交叉印证——在数学/代码之外，先回答「这个任务的 reward 是能被精密规则算出来（reward function / implicit PRM 式计算），还是只能靠 golden label 标出来」，再决定系统形态；直接上 LLM-as-judge 前，先按邵凡与方家瑞给出的量级（千级并发、TPM 上限）算一遍系统账，远程在线服务扛不住批量 judge 已是现场共识，in-rollout reward server 分卡部署是当前主流解法。
  • 去中心化的默认答案是 disaggregation 而不是多方共识：若需求是「把 RL 流程的一部分放到本地/安全处执行」（自定义 reward function、agent loop），方家瑞判断的云产品/API 形态比多方协同训练更接近落地；张涵的拜占庭与挖矿激励提醒，适用于任何「众包算力做 RL」的提案评估。
