2一句话总结

LightLLM v1.0.0 的主线是把框架开销压到只剩推理本身：用共享内存 Req 对象 + ctypes 直读消灭进程间序列化，用调度/预处理/后处理与推理的折叠提高 GPU 利用率，再用「历史分布预测输出长度 + 按请求退出时刻算 batch 峰值显存」的调度在安全与利用率间取最优；面向 DeepSeek 的部分则给出 MLA 在 prefill 用解压缩方案、decode 用 Q 吸收方案的分工结论，并已跑通 PD 分离原型（同等机器口径下 decode 时延 P25/P50 约从 160ms 降到 100ms，字幕口径）。

3核心

架构回顾与 v1.0 的通信改造：进程间只传一个 req id

LightLLM 一贯的设计原则是轻量、可读、扩展性高，v0 时代的两个关键特性是多进程架构 + 异步 CPU/GPU 处理，以及按 batch 峰值显存（而非进入时刻显存）估算的调度策略（page size 取 1 也是为这套调度服务）。旧架构的问题在高并发下暴露：三进程间靠 ZMQ 通信，序列化/反序列化开销大；调度与推理串行，拖低 GPU 利用率。

v1.0 的解法是引入可跨进程读取的 Req 对象：把采样参数、token id 等请求信息放进基于共享内存的结构体，进程间只传 req id，各进程用 Python ctypes 接口直接从内存读对象，序列化开销基本归零（代价是 ctypes 调用本身不如 Python 原生接口快，讲者判断已不构成瓶颈）。HTTP server、router、detokenizer 之间改用共享内存循环队列传信号；router 与 model RPC 之间也不再传 input ids 等大字段——model RPC 常驻等待 event，router 调度后只置位标志即触发推理。讲者提到 SGLang 团队解决同类问题的方式是把 router 与 model 进程「缩在一起」并按 TP 份数复制 router，LightLLM 因请求对象已在共享内存，无需这一步。

折叠：把调度与前后处理的时间藏进推理

除调度与推理折叠（推理 batch $i$ 的同时调度 batch $i+1$ ）外，v1.0 还实现了更激进的版本：把推理前的元数据打包预处理、推理后的后处理也折叠进推理时间。该模式尚未默认开启（测试不充分），讲者建议感兴趣者在代码里手动打开；在高并发、请求输入输出都很短的场景（推理本身开销小、处理开销占比高）下收益最大。

调度：输出长度预测 + 峰值显存估计（全场最有方法论含量的一段）

单机场景下（PD 不分离、KV cache 容量有限）调度策略直接决定 SLA 约束下的吞吐。讲者先摆出两种极端：

  • 保守式：按 max_tokens 预留显存，能放下才准入——绝不逐出请求，但 GPU 利用率低；
  • 激进式：先放进来再说，显存不够就暂停/逐出部分请求事后重算——利用率满，但被逐出请求的用户体验受损。

LightLLM 的方案分两半。其一是输出长度预测：观察 OpenAI 等公开数据发现，相邻时间窗口内的输出长度分布相对稳定（对话数据更稳，API 数据对角线相关性也成立），于是用历史请求输出长度分布，在每个调度步对 batch 内每个未结束请求重新采样其剩余长度——从「大于当前已输出长度」的条件分布里采样，预测值大概率大于真实剩余长度、又远小于预设 max_tokens，并随生成推进不断收窄。其二是峰值显存估计：一个 batch 的真实峰值不是各请求显存的简单相加，而是出现在某个请求退出时刻；把各请求按预计退出时刻排序，逐个时刻累加存活请求的占用取最大值，即得该 batch 整个执行期的显存峰值——这是精确估计，不会因多放请求导致暂停或逐出。配合 page size 等于 1 的细粒度管理，效果是「几乎最安全、且能把显存利用满」。实验对比表（字幕口径，具体数值在 slide 上未逐一口播）显示：相对激进调度峰值显存略低，但请求逐出率大幅下降；长输出的 decode-heavy 场景收益最明显，长输入短输出的对话场景各策略差别不大。讲者还指出这套调度可随线上分布漂移在保守与激进两端自动退化适配。相关论文已被录用（Q&A 中讲者说当时网上还搜不到，年后才中，细节待交流群公布）。

张量管理器：让同 shape 张量跨层共用一块显存

推理时显存吃满后，PyTorch 默认分配器因碎片化导致张量分配效率骤降。LightLLM 的张量管理器替换了 torch 的默认分配函数，手法是接管引用计数：把推理中每层同 shape 张量手动计数、令其永不归零，从而让每一层都复用同一块地址调用自有 alloc。收益最大的场景是 prefill 阶段且显存用得很满时。同一机制还优化了 CUDA graph 的显存：按 batch 从大到小捕获 graph 时，小 batch 的张量与大 batch 共用同一块地址，所有 graph 在显存上只剩 graph 本身的开销——于是 decode 侧可以放心开很多 graph（服务 100–200 并发时显存依然够用）。讲者把框架显存优化归为两块：prefill 的张量复用 + decode 的 graph 显存共享。

量化支持：layer 级混合精度 + 在线量化

LightLLM 自称提供业内较丰富的量化支持，并适配了 vLLM、TensorRT-LLM 等框架的量化格式（字幕口径）。两个实用点：加载浮点模型时若配置指定了量化类型但无量化信息，可在线做 min-max 量化（讲者认为 INT8/W8A8 这类精度足够）；配置文件支持 layer 级混合部署——例如 W8A8 时发现某些层敏感，可单独把 down 层等敏感层排除在量化外或指定其他比特，与 BF16 混合，日志会打印每层的量化设置方便 debug。

PD 分离原型：master 注册制 + KV 只传缺失部分

PD 分离目前是原型实现：启动 master 节点后，prefill 与 decode 节点主动上报注册，master 据此动态增删 P/D 节点；各节点定期向 master 汇报 KV cache 负载，供请求分配时调度（当前调度方法还比较初级，讲者明确邀请社区贡献 PD 调度策略）。请求侧流程：P 节点推理后创建一个 KV 传输子进程，先与 D 节点协商——双方都维护 KV cache，D 侧已有部分则只传缺失部分，长文本场景省传输；短文本可省略协商直接传。讲者坦白原型未充分优化，但 SLA 收益已可见：对比实验为 1P1D（两台机器）跑 100 并发 vs PD 不分离（一台机器）跑 50 并发，PD 分离的 decode 时延明显更低，P25/P50 口径约 100ms 对 160ms（字幕口径）；Q&A 中讲者解释了并发数为何不同——1P1D 用 16 卡对 1PD 的 8 卡，等机器口径下若用 2 个 PD 实例则只需各跑 50 并发、时延只会更好。他对 PD 分离的定位是：P/D 解耦后调度策略选哪种对 SLA 的影响都大幅减小，因为 prefill 与 decode 已不再互相干扰。扩缩容实践上一般按固定 P:D 比例进行。

DeepSeek 专项：MLA 的 prefill/decode 分工与算子负载均衡

MLA 部分讲者系统比较了四种方案（KV 存压缩或解压缩 × attention 时是否做 Q 吸收/权重融合）：矩阵吸收会把 attention 的 head dim 从 128 涨到 576，prefill 计算量显著变大；decode 本身计算密度低，各方案计算量差别不大。结论是分工：prefill 存压缩 KV、解压后再做 attention（方案二）；decode 存压缩 KV、直接用 Q 吸收（方案三）——兼顾 KV 占用小与计算量小。算子侧对 MHA decode 做了负载均衡改进：原实现按 max request length 划 block，请求长短不均时浪费严重，改按设备 SM 数量对不同长度请求做负载均衡，极端长短不均场景有明显收益（slide 对比，字幕口径）。此外也提及 MoE 模型的推理优化，具体细节让观众看博客与代码。

部署与性能对比、路线图

部署支持单机、双机直至多机。单机关键参数是 CUDA graph 的 max batch size（默认 100，即捕获 1–100 的 graph；得益于张量管理器，graph 显存开销可控）；双机需另设 master 地址与各 rank 编号，四机类推。性能对比（讲者注明是两周前测的版本，对比对象为当时的 vLLM 与 TensorRT-LLM 0.17.0，均已继续迭代）：100 并发、输入长度服从均值 128 的高斯分布一类设置下 LightLLM 有微小领先，讲者归因于框架开销已被折叠殆尽——「开销基本都在推理层」。路线图：正在接入 DeepSeek 官方的 DP+EP（含 DP+TP+EP）部署方案，预计一到两个月完成通信计算折叠；PD 分离后续做高阶调度（处理 P/D 峰值时序错位）与异构方案（P、D 可用不同并行策略与量化方案）；也提到 GEMM 与通信折叠、micro-batch 计算分析等方向在实践中。团队自陈精简，迭代速度有限，呼吁社区共建。

Q&A 散点

  • PD 分离为何也能降 prefill 时延：prefill 是计算密集型，100 并发下排队处理（默认 chunk 16K）会拉长首字延迟，独立 P 节点后排队可控。
  • PD 分离 vs 传统 chunked prefill：讲者坦承没做过数据对比；混合执行也能降 decode 时延，但理想情况下 P/D 物理分开 SLA 体验更好，后续会补对比。
  • MLA 两阶段可否混合执行：两阶段存的都是压缩 KV，只是 attention 函数不同，开两个流异步跑即可混合。
  • H20 能否跑：可以（单卡 90 多 GB 显存），但团队没有 H20 机器、未测性能。
  • 两台机器吞吐：两台 A100 级机器略逊于单台 H200（跨机 RDMA 开销），但基本同级；等 DP+EP 接入后会放多机 H200/H100 数据。
  • 多机部署细节：用 torch distributed，需手动传 master_addr（NCCL 不提供现成的通讯组 IP 获取接口）。

5可迁移

  • 「按退出时刻算 batch 峰值显存 + 条件分布预测剩余长度」是一套可移植的准入控制：任何 KV cache 受限的推理服务（包括自研 rollout 引擎）都能用它替代 max_tokens 预留或先到先得，把「不逐出」与「高利用率」同时拿到；对 RL rollout 这种输出长度方差极大的负载尤其对症。
  • 框架开销优化的顺序值得抄：先消灭序列化（共享内存对象 + 只传 id），再做调度/前后处理与计算的折叠，最后才抠算子——LightLLM 的对比优势主要来自前两步而非 kernel。
  • PD 分离的 KV 协商「只传缺失部分」与 P/D 异构（不同并行/量化策略）是做 disaggregated serving 时值得预留的接口；且讲者判断解耦后调度策略的重要性下降，资源应先投在传输与配比上。

6疑问 / 下一步

  • 输出长度预测依赖「相邻时间窗口分布稳定」这一经验观察；负载突变（如 RL 训练中 prompt 分布随轮次漂移）时预测失效的幅度和逐出率回升曲线，讲授未给。
  • PD 分离原型的 master 调度目前较初级：P 与 D 的峰值天然错位（P 先峰值、D 后峰值），讲者列为待解的高阶调度问题，具体方案与收益待后续版本与数据。
  • 与 vLLM/TensorRT-LLM 的性能对比是两周前的旧版本数据且 LightLLM 仅「微小领先」；在 DP+EP 接入后多机场景的实测（讲者承诺放多机 H200/H100 数据）值得回访核对。
