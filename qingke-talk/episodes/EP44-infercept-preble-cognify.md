## 一句话总结

讲者把 agent 上生产拆成三层基础设施问题：调优层靠 Cognify 的分层自适应搜索，在几美元、几十分钟内替人工找 agent 工作流的好配置；serving 层靠 Preble 的前缀感知分布式调度，把大量共享的长 prompt 的重复 prefill 变成可复用的缓存调度问题；拦截层靠 InferCept 在工具/数据调用打断生成时，用统一的「GPU 浪费」度量在丢弃重算、保留显存、换出 CPU 三种 KV 策略之间逐请求动态选择。

## 核心

### 问题定位：agent 的生命周期瓶颈不在写代码那一段

讲者开场给出一组口径数字：企业通常一个月内能做出 agent demo，但约有 80% 的项目从未进入生产，进入生产平均约需九个月；与咨询公司交流得知，把 demo 做成生产系统要多花至少五倍时间（字幕口径）。demo 易、生产难的原因有二：一是推理成本在涨——训练成本在降，但多步 agent（客户案例中单系统已超过 80 步模型/工具调用）让推理成本持续攀升；二是 agent 的开发生命周期（构逻辑、备数据、写 evaluator、反复调优、上 serving、加监控、再回炉）里，框架工具只覆盖了上半段，后半段的调优、部署、拦截处理才是真正耗时之处。本期的三件工作正好对应后半段的三处。

### Cognify：把 agent 调优自动化成一个分层搜索问题

调优的困难在于搜索空间组合爆炸：一个只有 3 次 LLM 调用的小工作流，假设有 12 个配置维度、每个维度 3 个选项，全空间就有几十万种组合；按每次执行约 \$10/百万 token 的口径估算，穷举成本约 \$55,300、耗时数周（字幕口径）。而实际问题只需要：能否用很少的试验（哪怕 8–10 次）、\$5 以内、30 分钟以内，找到足够好的配置？

Cognify 的做法叫自适应分层搜索（Adaptive Hierarchical Search）：把配置维度按抽象层级分成三层——顶层是**架构调整**（改工作流结构，如任务分解、任务合并）、中层是**步骤配置**（每步换模型、重写代码）、底层是**权重/提示词配置**（推理提示、few-shot 示例等）。分层之后每个候选只需在低维子空间里比较，搜索效率远高于在完整高维空间里跑贝叶斯优化（讲者明言贝叶斯优化在高维下效果差）。预算按层级复杂度分配；在提示词层使用 successive halving（字幕音作「成功哈维」）淘汰较差的半数候选、把剩余预算追加给表现更好的分区。系统会返回一整条 Pareto 前沿，而不是单一最优解，由用户按质量/成本/延迟的偏好自选。

成绩（字幕口径）：在六类工作负载（RAG 问答、text-to-SQL、数据可视化、多智能体金融分析、代码生成、BIG-Bench 一类任务）上，质量最高提升 2.8 倍、延迟最高降低 2.7 倍、成本最高节省 10 倍；整个搜索只花约 \$1.5–10、8–42 分钟，耗时约为对比优化工具（如 DSPy 类工具，字幕作「DS」）的一半且结果更好。text-to-SQL 示例里，一个候选把质量再抬高 15 个百分点的同时把成本与延迟大幅压低，另一个候选质量涨幅最大（46%）但成本/延迟收益较小——这正是要返回 Pareto 前沿的原因。

讲者据此主张造 agent 的第三条路线：既非全手工调参，也非让 LLM 一次性生成整个 agent，而是**人写初始工作流（生产环境必须把业务逻辑先钉住）、机器自动调优**，并称这条路线「至少目前已在生产环境中使用」。

### Preble：长共享 prompt 是一个分布式缓存调度问题

第二部分换到 serving：agent 时代的 prompt 不再是短问题，而是系统提示 + 工具说明 + few-shot + 长文档/长视频块的复合体。讲者在五类工作负载（工具型问答、具身 agent、程序生成、视频分块问答、长文档问答）上的观察是：prompt/output 长度比非常高，且**超过 80% 的 prompt 内容在至少两个请求之间共享**。

今天的分布式 serving 对此不敏感：轮询式调度把共享同一前缀的请求打散到不同 GPU，每块 GPU 都要重算前缀。应该做的事，是把请求发往已经缓存了其前缀 KV 的 GPU；但盲目追逐缓存又会让持有热门前缀的 GPU 过载。Preble 的核心是 E² 算法（字幕口径，exploit/explore 双策略）：比较共享前缀长度与请求独有部分的长度——共享前缀更长就**利用**（发往已缓存该前缀的 GPU，省重复计算），更短就**探索**（发往负载较轻的 GPU 做均衡）；某个前缀过于热门时，系统自动把该前缀再平衡迁移到其他 GPU。负载度量不是简单的队列长度，而是由三部分累加：当前运行中的 batch、为给新请求腾显存需驱逐的 KV 占用、运行当前请求的成本；选总成本最低的 GPU。架构上是两级调度：全局调度器（重写，维护全局前缀树矩阵与再平衡器）+ 每 GPU 本地调度器（公平队列），本地完成调度后回传负载更新。系统建于 SGLang 之上。

成绩（字幕口径，个别数字字幕语序混乱、仅供参考）：相比基线，平均延迟下降约 1.5–14 倍区间、P99 延迟下降约 2–10 倍。讲者说该工作 2024 年 5 月发布后，Anthropic、OpenAI 等生产系统都开始支持前缀共享与更便宜的共享计费；还有一篇最佳论文级工作直接受 Preble 启发（实验室名与机构名字幕识别不清，本文不写）。

### InferCept：工具调用打断生成时，KV 缓存该怎么办

第三部分处理 tool/data 调用（今天即 MCP 服务器调用）。讲者先给出真实工作负载画像：六组真实场景（数学、QA、虚拟环境、聊天、图像生成、文本转语音），单请求有约 2–28 次工具调用，上下文可长到每请求约 20 MB 量级（字幕口径）。

问题在于：今天的 serving 系统（如 vLLM 一类）不处理这种拦截——工具调用被当作请求结束，全部 KV 缓存直接丢弃，工具结果回来后再把整个前缀重算一遍；讲者口径是这会浪费最高约 40% 的 GPU 资源，并在端到端延迟上再加约 40% 的开销（字幕口径）。InferCept 给出三条可选策略及各自的权衡：

- **丢弃重算**：生成期间显存可借给别的请求，但返回时要全量重算 KV——单次重算可超过 200 ms（字幕口径），并让并发请求等待时间变长；
- **保留显存**：免于重算，但被占住的 GPU 显存会让其他请求无显存可跑；
- **换出到 CPU**：受限于 PCIe 带宽，换入换出要等带宽，且带宽要在多个等待请求间分配。

InferCept 把三种策略统一到一个度量——**GPU 浪费**：被占用（或被浪费重算所耗）的显存量乘以占用时间；每个请求按估算浪费最小者选策略。三种策略各自也做了优化：丢弃侧做分块重算（逐块重算 token 以复用空闲算力）、换出侧做分层流水线换出（逐层换出与前向重叠），并以「谁的保留/丢弃浪费最大」为优先级分配稀缺的 PCIe 带宽。结果（去年工作，字幕口径）：在 6B 与 13B 模型、六种工具混合负载上，请求率（吞吐）达基线的 1.6–2 倍，延迟改善约 1.3–12 倍区间。

### 讲者的总判断

2025 年是「agent 的元年」：开发框架与工具集已经很多（如 LangChain 一类，字幕作「长链」），但真正能投入生产的 serving 内核仍缺位——调优自动化、长共享前缀的分布式调度、工具拦截下的 KV 管理这三块，正是其实验室跨层补齐的对象。

## 可迁移

- 对 agent serving 的一个直接清单：上生产前过三件事——(1) 调优预算：先手动钉住工作流结构，再用分层搜索（架构/步骤/提示词三层，提示词层用 successive halving）自动找配置，并保留 Pareto 前沿而非单最优点；(2) 前缀调度：统计请求间 prompt 共享率，若共享超过半数，把调度目标从「负载均衡」改成「缓存亲和性 × 负载」的联合度量，且要给热门前缀留自动再平衡的口子；(3) 工具拦截：统计每次工具调用造成的 KV 浪费显存×时间，丢弃、保留、换出三者按请求逐个算账，不要全局写死一种。
- InferCept 的「GPU 浪费」是很好用的统一记账单位：把显存占用时间做成成本函数后，很多 serving 取舍（重算 vs 占用 vs 换出带宽）都能归一到同一把尺子上，比拍脑袋选策略稳健。
- Cognify 的层级抽象对 RL/post-training 调参同样成立：结构性改动（数据/算法骨架）、步骤级改动（模型/并行策略）、连续/文本级改动（提示、超参）本就该有不同的搜索预算与淘汰节奏；把 successive halving 只放在最便宜的一层，符合「越便宜的试验跑得越多」的原则。
