## 一句话总结

冷启动的对话推荐 agent 没有真实用户交互可训——Spotify 先把单轮 prompt 规划成对话计划，再由 UserLLM 实现成多轮对话，用 LLM-as-judge 评估，合成对话直接替代真实用户做测试集；再跑自改进循环，对同一问题多次采样算方差，把失败拆成可靠性失败（高方差，同 prompt 结果不稳定）和能力缺口（低方差但系统性错），前者走方差对比优化，后者交给 coding agent 自动修 prompt / 工具描述 / planner 配置。合成对话的人工评审四维都在 90% 以上；质量在已经高度优化过的人工 prompt 之上又涨了 8%；线上 A/B 两周、约 1,500 万用户，收听时长 +14%，WAU +5%，跳过率 −5%。但长对话还是难：7 turn 比 2 turn 的 pass@1 低 11.9 个点。

## 3 个问题

1. 方差拆分在什么情况下会把能力缺口误判成可靠性失败？高方差 = 不稳定、低方差 + 系统性错 = 能力缺口，这个二分法假设“采样方差”能干净地分离两种失败。但采样方差本身受温度、采样数、judge 噪声影响：一个能力缺口如果恰好落在模型“有时蒙对”的边界上，方差会被抬高、误判成可靠性问题，于是走方差对比优化（白费力气），而不是让 coding agent 去修 prompt。设计一个实验：先人工标注一批失败案例的真实原因（可靠性 vs 能力缺口，作为金标准），三臂——A 温度 0.7 采样 8 次、B 温度 1.0 采样 8 次、C 温度 0.7 采样 32 次——每臂都用方差阈值做分类，与金标准比分类准确率；再记每臂误判案例的共同特征（judge 打分是否接近阈值、任务是否跨多工具）。判据：若 C 的准确率 ≫A、且误判集中在“方差接近阈值”的案例 → 误判主因是采样噪声，增大采样数可解；若三臂的误判都集中在同一批案例、且与采样数无关 → 误判是系统性的（这类失败本身就是“边界型能力缺口”），方差拆分在这个区域失效。再预测一个 2×2 格子：{低方差，高方差} × {judge 一致，judge 分歧}，哪个格子最可能是真能力缺口并写理由。漏洞：金标准本身就是人工标注——标注者对“能力缺口”的判断可能与 coding agent 能不能修好它并不一致（标注为能力缺口、但修 prompt 修不好）；而且三臂的采样成本不等，C 的准确率优势可能只是“花了 4 倍算力”，没有控制成本就比不出机制。
2. 合成测试集的天花板在哪里——UserLLM 和 judge 是不是在互相放水？合成对话替代真实用户做测试集的前提，是 UserLLM 演的用户足够真、judge 的打分足够准。但 UserLLM 和被测 agent、judge 很可能来自同一模型家族、共享同一种“好对话”的偏见：UserLLM 只会提 agent 擅长回答的那类请求，judge 只会奖励自己家族的说话风格，于是合成测试集上的 +8% 可能在真实用户身上缩水。设计一个实验：固定同一批 prompt 变体（人工优化版 vs 自改进循环版），三臂评估——A 合成测试集（UserLLM + LLM-as-judge）、B 真实用户日志回放（有真实交互的留存样本）、C 交叉模型评估（UserLLM 与 judge 换成另一个模型家族）。评三臂下两个版本的相对排序与差距大小。判据：若 A 与 C 的排序一致、但 B 的排序翻转或差距大幅缩小 → 合成测试集的天花板是“家族内偏见”，不是 judge 能力；若 A 与 B 排序一致、只有 C 翻转 → 问题在 judge 的家族偏见，UserLLM 本身没问题。再构造一个具体反例：用户说“推荐点我没听过的意大利独立音乐人”——UserLLM 演的用户会接受任何“听起来像意大利独立”的推荐，但真实用户会立刻听出是不是自己真没听过、是不是真喜欢；若合成测试集上这个请求 pass 率很高、真实用户跳过率也很高，说明 UserLLM 根本演不出“品味”这一维。漏洞：B 的真实用户日志是“已经上线后才有的”——冷启动阶段根本没有 B，实验只能在事后做，事后验证通过不等于事前能用合成测试集做决策；而且 B 的样本是“愿意用旧版功能的用户”，与 A/B 测试里 1,500 万新用户的分布不同。
3. “只修 prompt、不动模型”能搬到 Day 04 ToolLoop 的工具数据上吗？Spotify 的自改进循环修的是 prompt / 工具描述 / planner 配置，模型权重一动不动；ToolLoop 的闭环是“出错就带着错误原因重生成数据再训模型”。两者都靠反馈循环，但一个修规划层、一个修模型层。设计一个实验：拿 ToolLoop 的工具调用任务，三臂——A 只修 prompt / 工具描述 / planner（Spotify 式，模型冻结）、B 只重生成数据再 SFT（ToolLoop 式，prompt 冻结）、C 两者都做；每臂内部再按 Spotify 的方差拆分，把失败分成可靠性失败与能力缺口两组，分别看三臂在两组上的提升。判据：若 A 在可靠性失败组 ≫B、但在能力缺口组 ≈B → “修 prompt”只对不稳定问题有效，能力缺口必须动模型；若 C 在两组上都 ≫A、B → 两层都得修，Spotify 的“不动模型”只是工业上线快、不是上限高。再预测一个 2×2 格子：{可靠性失败，能力缺口} × {修 prompt，训模型} 在准确率提升上的排序并写理由。漏洞：三臂的“修”都依赖同一个 coding agent / 同一套反馈信号——A 修不好的 prompt 缺口可能只是 coding agent 不会修，不是 prompt 层修不好的证据；而且 ToolLoop 的任务是工具调用、Spotify 的任务是推荐对话，两边失败的定义本来就不等，直接搬过去可能只是在比任务难度。

## 核心机制

1. **Motivation**：对话推荐 agent 是内容发现的新范式，用户用自然语言表达复杂意图（例如“推荐点我没听过的意大利独立音乐人”）。最大的瓶颈是 agent 规划——选什么工具、按什么顺序调——而冷启动阶段根本没有真实用户交互可用来优化。等真实用户来了再迭代，太慢；不上线又拿不到数据。这是一个先有鸡还是先有蛋的问题。
2. **方法**：合成数据 pipeline——先把单轮 prompt 规划成对话计划，再由 UserLLM 实现成多轮对话，用 LLM-as-judge 评估，合成对话直接替代真实用户做测试集；自改进循环——对同一问题多次采样算方差，把失败拆成可靠性失败（高方差，同 prompt 结果不稳定）与能力缺口（低方差但系统性错），前者走方差对比优化，后者交给 coding agent 自动修 prompt / 工具描述 / planner 配置。整个过程没有微调模型，修的是 agent 的规划层。
3. **关键数字**（论文自报，经本系列 papers.md 注释与 arXiv 摘要核实）：合成对话的人工评审四维都在 90% 以上；质量在已经高度优化过的人工 prompt 之上又涨了 8%；线上 A/B 两周、约 1,500 万用户：收听时长 +14%，WAU +5%，跳过率 −5%；但长对话还是难：7 turn 比 2 turn 的 pass@1 低 11.9 个点。

$$ \mathrm{Var}(r) = \mathbb{E}\left[(r - \bar{r})^2\right] \quad\text{；}\quad \text{高方差} \to \text{可靠性失败} \quad\text{；}\quad \text{低方差且系统性错} \to \text{能力缺口} $$

## 边界

- 方差拆分的阈值没有公开口径：注释没有说“多高算高方差、采样几次、温度多少”——阈值一变，可靠性失败与能力缺口的划分就跟着变，这个拆分本身没有独立验证。
- 合成测试集的天花板：UserLLM 演的用户 + LLM-as-judge 的评估都在同一模型家族内完成——合成对话的人工评审四维都在 90% 以上，评的是“对话像不像真对话”，不是“测不测得出真实用户的品味与挑剔”。
- 长对话仍是短板：7 turn 比 2 turn 的 pass@1 低 11.9 个点——对话越长，规划错误越容易累积；自改进循环修 prompt / planner 配置，没有解决“多轮状态越攒越乱”这个根本问题。
- 线上 A/B 的对照组是“只支持 session refinement 的旧体验”：+14% 收听时长里有多少来自“对话推荐”本身、多少来自“终于有了个能聊天的入口”，论文没有拆分——新功能上线自带的新鲜感效应没有排除。

## 迁移

- “合成数据当测试集”可搬到任何冷启动 agent：没有真实用户之前，先用 UserLLM + judge 搭一个可跑的评估环——关键是先把“对话计划”这层显式化（单轮 prompt → 对话计划 → 多轮对话），而不是直接让 LLM 自由发挥编对话；没有计划层，合成对话的覆盖度全靠运气。
- “失败先拆分、再分流”可搬到任何自改进循环：Day 02 AED 是把失败诊断进 SFT，Day 04 ToolLoop 是带着错误原因重生成，Day 06 ToolRACER 是把失败轨迹喂回模拟器再生——Spotify 多做了一步：先按方差把失败分成两类，再决定修哪一层；不拆分就全量重训，是把两种不同性质的问题混在一起治。
- 与 Day 04 ToolLoop 构成对照：ToolLoop 证明无反馈合成数据比不训还差（−2.17 个点），Spotify 的自改进循环同样是闭环，但修的是 prompt / 工具描述 / planner 配置、模型权重不动——闭环的价值不在“训不训模型”，在“失败信号有没有回流到能修它的那一层”。
- 如果复现，第一步先搭“对话计划”层（定义一个单轮意图能展开成哪些多轮计划、每步调什么工具），再写 UserLLM 的 persona（它要演的用户得有明确的品味、预算、耐心上限，否则演出来的全是“好好好”）；没有这两层，合成对话测不出任何东西。
