# WebHarbor: Docking Real Websites for Evolving GUI Agent Environments

> 📖 阅读版：https://papa-panda.github.io/post-training/synthetic-data/day-13-webharbor/

## 元信息

- Title: WebHarbor: Docking Real Websites for Evolving GUI Agent Environments
- Authors: Wang 等
- Link / arXiv: https://arxiv.org/abs/2611.03634
- Date of publication: 2026-11-02
- Tags: [web-environments, offline-replay]
- 与前篇的关系：Day 03 WorkForge 说“真实工作空间才是瓶颈”，16.7K 真实工作空间让 agent 学会探索；WebHarbor 是同一条真实感路线在网页 GUI 上的版本——只不过 WorkForge 是“从真实资源建工作空间”，WebHarbor 是“把真实网站整个靠岸搬进离线环境”，真实感从“文件和工作流”升级成“整个网站的前后端 + 状态”。Day 12 CUA-Master 用快照回滚解决“长任务失败了怎么接着试”，WebHarbor 解决的是更底层的问题：快照回滚需要一个“状态可恢复、可反复进”的环境，而真实网站恰恰不可恢复——页面会变、登录会过期、后台状态改了回不去；WebHarbor 的离线重建，正是给 CUA-Master 那类方法造了一个“能回滚的家”。Day 01 SPADE 让环境自己长出来、30B 一轮 400 步生成 3310 个环境，WebHarbor 走的是完全相反的路：57 个人花约 5 个月，一个一个把真实网站手工靠岸——合成环境的“量”和真实环境的“真”，这篇是系列里最贵的对照组。Day 09 Agent-R² 用真实附件 + 交付级 rubric 治“不读附件、不验算就交文件”，WebHarbor 用“前后端 + SQLite 状态”重建治“网页 agent 练不了登录后流程”——两者都信“真实的东西不能只贴个皮，状态和流程都得搬进来”。

## 一句话总结

网页 GUI agent 缺的不是模型，是能反复练、不会变的练功房：真实网站评测时内容会变、登录会过期、登录后的流程根本覆盖不到，而合成环境又缺功能深度和视觉保真度。WebHarbor 把真实网站“靠岸”——按目标任务定范围，重建前后端加 SQLite 状态，逐步执行修补缺失页和状态转移，人工评审视觉、功能、任务有效性——造出 153 个可执行、可 Docker 化的离线网站环境，含 3518 个多步与登录后任务；离线环境里练出来的 agent 迁移到真实网站 WebVoyager 上 81.2%，但迁移到 WebArena 只有 28.8%，而建这套环境的代价是 57 个人约 5 个月。

## 3 个问题

1. 离线复现的保真度天花板在哪里？——取 papers.md 的思考题。离线环境迁移到真实网站 WebVoyager 81.2%，但迁移到 WebArena 只有 28.8%，两个数之间差了 52.4 个百分点，约 2.8 倍——同一个离线环境，换个真实基准，迁移率直接打了三折。三臂——A 离线重建环境（论文方法：153 个环境、3518 个任务，重建前后端 + SQLite 状态、人工评审三维）；B 真实网站直接评测（不重建，在真实网站上跑同样的任务）；C 合成环境（LLM 凭空生成网站与任务，不锚定真实网站）。指标：迁移成功率（离线任务成功率 → 真实网站同任务成功率）、多步任务完成率、登录后任务完成率、每任务平均修复轮数（逐步执行修补缺失页 / 状态转移的次数）、人工评审三维各自的通过率（视觉、功能、任务有效性）。判据：若 A 在 WebVoyager 上 81.2% 但在 WebArena 上 28.8%，且 B 在两个基准上都稳定 → 天花板不在“重建技术”，在“基准本身的任务分布”——WebArena 的任务可能恰恰落在重建没覆盖的功能上（比如需要真实第三方登录、真实支付、真实时间敏感内容），离线复现保真度的上限由“哪些功能能被重建”决定，而不是“重建得多像”；若 A 在两个基准上都 ≈ B → 离线复现基本没有保真度损失，28.8% 是 WebArena 本身就难，不是重建的锅；若 C ≈ A → 重建的“真实网站锚定”没带来什么，LLM 凭空合成的网站也能迁 80%，那 57 人 5 个月的重建成本就是白花的；若 A 在登录后任务上 ≫ C、但在未登录任务上 ≈ C → 保真度的价值集中在“登录后流程”这一块，别的任务用合成环境就够了。再预测一个 2×2 格子：{离线重建，合成环境} × {登录后任务，未登录任务}，哪个格子的迁移率最高、哪个最低，并写理由。再构造一个具体反例：离线重建的 81.2% 迁移率可能不是“保真度高”，而是“任务挑得好”——WebHarbor 的任务是“按目标任务定范围重建”的，重建范围本身就是按任务划的，任务天然落在重建过的功能里；换一批没在重建范围里的真实任务，迁移率可能直接掉到 WebArena 的 28.8% 那一档；更糟的是人工评审的“任务有效性”可能把“难复现的任务”提前筛掉了——评审通过的 3518 个任务，本身就是“能被重建的任务”，81.2% 是在“已被筛选过的任务”上量的，不是“真实网站任务全体”上的数。漏洞：81.2% 和 28.8% 各自的分母是什么，注释没说——是“离线环境里成功的任务里有多少在真实网站上也成功”，还是“真实基准全体任务”？如果是前者，28.8% 还要再打折；而且 153 个环境、3518 个任务，平均每个环境约 23 个任务——任务分布在环境之间均不均匀吗？有的环境 100 个任务、有的只有 3 个，迁移率是按任务平均还是按环境平均，注释没给；57 人约 5 个月也没有拆分——多少人力花在重建、多少花在人工评审，哪个环节最贵，不知道。
2. 成本这么高，什么任务值得建？——取 papers.md 的思考题，综合 Day 01 SPADE 与 Day 03 WorkForge。WebHarbor 建 153 个环境花了 57 个人约 5 个月；Day 01 SPADE 30B 一轮 400 步生成 3310 个环境，机器一轮就干完了；Day 03 WorkForge 16.7K 个可验证环境，也是从真实资源自动建的。三臂——A 人工靠岸重建（论文方法：57 人约 5 个月，153 个环境、3518 个任务）；B SPADE 式自生成环境（30B 一轮 400 步，3310 个环境，无人工）；C WorkForge 式半自动真实资源建环境（16.7K 环境，真实资源 + 程序化 verifier，无大规模人工评审）。指标：单位环境成本（人月 / 环境）、单位任务成本（人月 / 任务）、迁移到真实网站的成功率、登录后任务覆盖率、环境随时间“变旧”的速度（真实网站改版后，离线环境多久失效）。判据：若 A 的迁移率 81.2% ≫ B、C，且 B、C 在登录后任务上接近 0 → 值得建的任务是“登录后、多步、真实网站独有”的任务——只有这些任务非人工重建不可，别的任务用机器生成就够了；若 A ≈ C ≫ B → 关键不是“人工”，是“锚定真实资源”——WorkForge 式的半自动真实资源路线能以零头成本拿到差不多的迁移率，57 人 5 个月就花冤枉了；若 B ≈ A → 合成环境也能迁 80%，那“真实网站靠岸”这个卖点就是假的，成本最高的路线反而最不值；若 A 的迁移率随真实网站改版在 3 个月内掉一半 → 离线环境是“易耗品”，建一次管不了多久，57 人 5 个月的投入要按“每季度重建一次”摊销，值不值要重新算。再预测一个 2×2 格子：{人工重建，自动生成} × {登录后任务，未登录任务}，哪个格子的“单位迁移率成本”最低、哪个最高，并写理由。再构造一个具体反例：57 人约 5 个月建的 153 个环境，可能大部分成本花在了“长尾功能”上——一个网站有 100 个页面，任务只用到其中 10 个，但“按目标任务定范围重建”如果范围定得太宽，90% 的重建工作量服务的是没有任务的页面；反过来如果范围定得太窄，agent 一走出任务预设的路径就撞上缺失页——“逐步执行修补缺失页”修的是任务走过的路，没走过的路还是断的，agent 一探索就掉坑。漏洞：57 人约 5 个月是“总人力”还是“峰值人力”，注释没说——57 个人是全职 5 个月，还是 57 个人断断续续参与、合计 5 个月人月？两种算法差一个数量级；而且 153 个环境的“环境”粒度是什么——一个网站一个环境，还是一个子域名一个环境？如果一个大网站被拆成十几个环境，153 这个数的水分很大。
3. 离线环境的“可演化”，和 CUA-Master 的“外层飞轮”，是同一件事吗？——综合 Day 12 CUA-Master。WebHarbor 的标题就叫“Evolving GUI Agent Environments”，方法是“环境随新任务扩展功能范围”；Day 12 CUA-Master 的外层循环是“世界–数据–模型飞轮，按能力缺口再采集”。三臂——A 任务驱动演化（论文方法：新任务来了，扩展环境功能范围，逐步执行修补缺失页 / 状态转移）；B CUA-Master 式缺口驱动再采集（按模型弱项采下一轮数据，环境本身不动）；C 固定环境、只换任务（环境建好就冻结，任务在已有功能里组合）。指标：新任务加入后环境的“功能覆盖率”变化、每轮新增任务数、新增任务的迁移率（WebVoyager / WebArena）、环境维护成本随轮数的曲线、agent 在“旧任务”上的成功率是否退化（演化有没有破坏已有功能）。判据：若 A 的新任务迁移率逐轮稳定在 80% 左右、B 的迁移率逐轮下滑、C 的新任务很快撞上“功能不够用” → 任务驱动演化是真本事——环境跟着任务长，迁移率才保得住；若 A ≈ B → 演化不演化无所谓，涨分靠的是“任务越来越多”，不是“环境跟着长”；若 A 的旧任务成功率逐轮下跌 → 演化在破坏已有功能——修补新功能时把旧的状态转移改坏了，“演化”成了“拆东墙补西墙”；若 C ≈ A → 环境根本不需要演化，建好一次就够用了，“Evolving”只是标题党。再预测一个 2×2 格子：{任务驱动演化，固定环境} × {早期任务，后期任务}，哪个格子的迁移率最高、哪个最低，并写理由。再构造一个具体反例：环境“随新任务扩展功能范围”听起来是演化，实际上可能是“任务清单驱动的打补丁”——每来一个新任务，就给环境打一个只服务这个任务的补丁；补丁越打越多，环境变成一堆“只为某个任务存在”的特设功能拼盘，agent 在这个环境里练出来的本事，是“在这个拼盘里找路”，不是“在真实网站上办事”；更糟的是人工评审的“功能正确性”只审“新功能对不对”，不审“新功能和旧功能冲不冲突”——两个任务共用一个 SQLite 状态表，一个任务的补丁改了表结构，另一个任务的状态转移就悄悄坏了。漏洞：WebHarbor 的“演化”有没有轮次数字，注释没给——演化了几轮、每轮加了多少任务、每轮迁移率怎么变，全没说；而且 153 个环境是“演化后”的总数还是“初始”数，也没说——不知道演化到底贡献了多少环境、多少任务。

## 核心机制

1. **Motivation**：网页 GUI agent 的练功房是个两难：真实网站评测时内容会变、访问受限、登录后的流程根本覆盖不到——评一次一个样，训更没法训；现成的合成环境又缺功能深度和视觉保真度——练出来的 agent 到了真实网站上不会办事。WebHarbor 要的是一个“既真又稳”的中间态：把真实网站整个搬进离线环境，视觉、内容、功能流程都按真实网站重建，但在确定性控制之下——同一个任务，今天跑和下周跑，结果一样；登录后的流程也能反复练。
2. **方法**：任务驱动的人机协作重建。先按目标任务定范围——不追求把整个网站 1:1 搬进来，只重建任务用得上的功能范围；再重建前后端加 SQLite 状态——前端页面、后端逻辑、数据库状态三件套一起搬，状态是可控的、可复位的；然后逐步执行修补缺失页和状态转移——让 agent（或人）一步一步走任务，走哪儿缺哪儿补，缺失的页面和状态转移现场补上；最后人工评审三维——视觉（长得像不像真实网站）、功能（点一点是不是真能用）、任务有效性（这个任务在这个环境里是不是真能完成、真能判对错）。环境随新任务扩展功能范围——新任务来了，环境跟着长，不是建好就冻结。
3. **关键数字**（论文自报，出自 papers.md 注释与论文摘要）：153 个可执行、可 Docker 化的网站环境，含 3518 个任务，覆盖多步与登录后流程；离线环境迁移到真实网站：WebVoyager 81.2%，WebArena 28.8%（有限）；环境建设成本：57 人约 5 个月；平均每个环境约 23 个任务（3518 ÷ 153 ≈ 23.0，由上述两数算得）；论文摘要另报：Qwen 4B 级 GUI agent 在 WebHarbor 里做 RL 训练后，能泛化到未见任务，在四个基准上与领先的开源 GUI 网页 agent 相当（无具体分数）。

离线迁移率：WebVoyager vs WebArena（示意，非论文公式）：

$$\frac{81.2\%}{28.8\%} \approx 2.8$$

其中分子是离线环境迁移到真实网站 WebVoyager 的成功率，分母是迁移到 WebArena 的成功率——同一个离线环境，换个真实基准，迁移率差约 2.8 倍；52.4 个百分点的落差，是这篇最值得追问的数字。

任务密度（由论文自报数字算得，非论文公式）：

$$\frac{3518}{153} \approx 23.0$$

其中 3518 是任务总数，153 是环境总数——平均每个环境约 23 个任务；但任务在环境之间的分布注释没给，平均数可能掩盖了“有的环境任务多、有的只有几个”的不均匀。

## 边界

- 81.2% vs 28.8% 只有一个对照、没有分母：迁移率的分母是“离线环境里成功的任务”还是“真实基准全体任务”，注释没说——如果是前者，28.8% 还要再打折；而且两个基准的任务分布不一样，落差可能反映的是“WebArena 的任务恰好落在重建没覆盖的功能上”，不是“重建技术本身”的问题。
- 153 个环境、3518 个任务，任务分布没给：平均每个环境约 23 个任务，但有的环境可能 100 个任务、有的只有 3 个——迁移率是按任务平均还是按环境平均，注释没说；任务少的环境可能根本没被好好评审过。
- 57 人约 5 个月没有拆分：多少人力花在重建、多少花在人工评审，哪个环节最贵，注释没说；而且 57 人是全职 5 个月还是断断续续参与、合计 5 个人月，两种算法差一个数量级——“成本这么高，什么任务值得建”这个问题，没法用这个数直接回答。
- 人工评审三维没有各自的通过率：视觉、功能、任务有效性各自过了多少、卡在哪一维上，注释没给——不知道重建的瓶颈是“长得不像”、还是“功能不对”、还是“任务本身无效”。
- “逐步执行修补缺失页”只修任务走过的路：agent 一走出任务预设的路径就撞上缺失页——离线环境的“真实感”只在任务覆盖的范围内成立，探索一出圈就露馅；Day 03 WorkForge 说“真实感是学会探索的原因”，WebHarbor 的真实感恰恰是“探索一出圈就断”的那种。
- 环境随时间变旧的速度没量：真实网站一改版，离线环境就过期——57 人 5 个月的投入要按“每季度重建一次”摊销，还是“一劳永逸”，注释没说；如果离线环境是易耗品，这篇的成本账要重算。
- Qwen 4B 级 agent“在四个基准上与领先开源 agent 相当”没有具体分数：四个基准是哪四个、各多少分、基线是多少，注释和摘要都没给——RL 训练的收益到底有几分，分不开。

## 迁移

- “按目标任务定范围重建”可搬到任何“真实系统太贵、不能反复练”的领域：企业内部工具（真实系统有权限、有真实数据，不能给 agent 随便练）、机器人操作（真实机器人贵、会坏）、客服系统（真实客户不能当训练数据）——关键是先定任务范围再重建，别追求 1:1 全搬；而且要像 WebHarbor 这样把“状态”一起搬进来（SQLite 状态表），只搬界面不搬状态，agent 练的是假流程。
- 与 Day 03 WorkForge 构成对照：WorkForge 说“16.7K 真实工作空间，真实感是学会探索的原因”，真实工作空间比 LLM 合成的多 5.4 倍文件、2.4 倍文件类型；WebHarbor 把真实感从“文件和工作流”升级成“整个网站的前后端 + 状态”——一个信“工作空间真”，一个信“网站真”。两篇合起来才是完整的真实感故事：环境要真，状态也要真；但 WebHarbor 的教训是反向的：真实感越完整，成本越高——57 人 5 个月 vs WorkForge 的自动建，真实感的边际成本是指数涨的。
- 与 Day 01 SPADE 构成对照：SPADE 30B 一轮 400 步生成 3310 个环境，机器一轮就干完；WebHarbor 57 个人约 5 个月才建 153 个环境——合成环境的“量”和真实环境的“真”，这篇是系列里最贵的对照组。搬过去要改的第一件事，就是先算清楚“哪些任务非人工重建不可”：登录后、多步、真实网站独有的任务才值得人工靠岸，别的任务用 SPADE 式自生成就够了；混在一起建，就是拿 57 个人的成本去干机器能干的活。
- 与 Day 12 CUA-Master 构成对照：CUA-Master 的快照回滚需要一个“状态可恢复、可反复进”的环境，而真实网站恰恰不可恢复；WebHarbor 的离线重建，正是给 CUA-Master 那类方法造了一个“能回滚的家”——两篇是上下游关系：WebHarbor 造环境，CUA-Master 在环境里练。但反过来，CUA-Master 的教训也适用：快照回滚依赖“状态可恢复”，WebHarbor 的 SQLite 状态是不是“快照级可恢复”、还是“只能整库重置”，注释没说——如果只能整库重置，回滚的粒度就很粗。
- 与 Day 09 Agent-R² 构成对照：Agent-R² 用真实附件 + 交付级 rubric 治“不读附件、不验算就交文件”；WebHarbor 用“前后端 + SQLite 状态”重建治“网页 agent 练不了登录后流程”——两者都信“真实的东西不能只贴个皮，状态和流程都得搬进来”。但 Agent-R² 的真实附件是“检索验证”来的，WebHarbor 的真实网站是“人工重建”来的——前者可规模化，后者不可；搬过去要改的，就是把“人工重建”里最贵的那部分（人工评审三维）换成程序化 verifier，像 WorkForge 的“程序化 + 语义”双 verifier 那样。
- 如果复现，第一步先拿 1 个真实网站、10 个任务，按目标任务定范围重建前后端加 SQLite 状态，人工评审三维，量“每任务人时成本”和“迁移到真实网站的成功率”——如果每任务成本超过 1 人天、迁移率低于 50%，先别扩到 153 个环境，回去收窄任务范围；再拿 10 个任务，在离线环境和真实网站上各跑一遍，量迁移率——如果 WebVoyager 式任务迁 80% 但 WebArena 式任务只迁 30%，先查“任务分布”再查“重建技术”，别一上来就加人手。
