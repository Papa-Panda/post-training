> 📖 阅读版：https://papa-panda.github.io/post-training/synthetic-data/day-10-toolspace/

## 元信息

- Title: ToolSpace: Scaling Tool-Centric Environment Synthesis for Long-Horizon Agents
- Authors: Dong 等
- Link / arXiv: https://arxiv.org/abs/2611.05036
- Date of publication: 2026-11-03
- Tags: [tool-dependency, executable-graph]
- 与前篇的关系：Day 03 WorkForge 说“真实工作空间才是瓶颈”，ToolSpace 把这句话落到工具层——环境不是工作空间，是工具之间的可执行依赖。Day 04 ToolLoop 也是工具调用数据合成，但它的做法是“分解生成 + 动态自反馈”，合成的工具调用仍由 LLM 编出来；ToolSpace 反其道而行之：工具调用关系不由 LLM 编，改由真实 MCP 执行轨迹里挖出来。Day 05 Data Turnstile 把多轮工具交互拆成 DAG、分角色验证，ToolSpace 同样是“图”，但图上的边是执行见证过的依赖，不是 LLM 判定的依赖——Day 05 的教训是“小模型上未加工合成数据有毒”，ToolSpace 的回答是三重验证只留能从初始状态成功重放的样本。

## 一句话总结

长程 agent 的工具环境一直是先造库、再让 LLM 编工具和任务——编出来的工具接口可能跟真实接口对不上，工具组合也没有真实执行背书，任务也很少跨环境。ToolSpace 把顺序倒过来：先从真实 MCP 服务的执行轨迹和开源 agent 语料里，用确定性规则（不用 LLM 判断）挖掘相邻调用之间的数据依赖、状态依赖和重试依赖，建成加权工具组合图，再把图聚类成环境；只有会改状态的环境才合成数据库，查询类和无状态工具直接重放录好的返回值；然后在图上做带状态检查和回滚的随机游走，把每条链反编译成带断言检查的自然语言任务，只保留能从初始状态成功重放的样本。35B 模型在七个长程工具基准上的均值从 23.0 升到 41.0（SFT 后）、再到 43.2（加 RL）；执行见证的边胜过 LLM 判定的边（45.8 对 37.8）。

## 3 个问题

1. “执行见证的边”到底比 LLM 判定的边好在哪里——是边本身更真，还是过滤更严？三臂——A 执行见证边（论文方法：确定性规则从真实轨迹挖依赖）；B LLM 判定边（同样从真实轨迹出发，但依赖关系由 LLM 判断、其余 pipeline 相同）；C LLM 判定边 + 论文的三重验证（V_state / V_trace / V_out）全开。指标：七个长程工具基准均值、任务重放成功率、跨环境任务占比。判据：若 A ≫ B ≈ C → 好处在“边本身”——LLM 判定的依赖哪怕过三重验证也补不回来，执行见证是不可替代的信息源；若 A ≈ C ≫ B → 好处在“验证”不在“边”——LLM 边的问题是假边太多，三重验证筛掉假边就够了，挖边的方式不重要；若 A ≫ C ≫ B → 两者都有功劳，边和验证是乘法关系。再预测一个 2×2 格子：{执行见证边，LLM 判定边} × {三重验证开，三重验证关}，哪个格子的跨环境任务占比最高并写理由。再构造一个具体反例：真实轨迹里两个工具恰好相邻出现——比如每次查完天气都顺手查日历——确定性规则会把“顺手”记成一条依赖边，图里多了一条假边；若 A 臂的图里这类“巧合相邻”占多数，45.8 对 37.8 的优势可能只是在比“谁的假边更少”，不是比“谁的边更真”。漏洞：B 臂的 LLM 判定边用的是哪个模型、什么 prompt，论文没给——换一个更强的判定模型，B 可能直接追上 A；而且“45.8 对 37.8”这个数字没有说清是在哪个基准、哪种设置下量的——如果是消融用的小规模子集，它未必能代表七个基准的整体差距。
2. 只给会改状态的环境合成数据库——这个“只合成一半”的分工，边界在哪里？三臂——A 论文方法（状态变更环境合成库，查询/无状态工具重放录好的返回值）；B 全部合成（所有环境都合成数据库，包括查询类工具）；C 全部重放（所有工具都重放录好的返回值，不合成任何库）。指标：任务重放成功率、跨环境任务占比、七基准均值、环境搭建成本（时间/算力）。判据：若 A ≫ B ≈ C → 分工本身是关键——合成库只该用在“状态会变”的地方，给查询工具合成库反而引入不一致；若 B ≈ A ≫ C → 合成库越多越好，“只合成一半”只是省钱的妥协，不是性能最优；若 C ≈ A ≫ B → 重放录好的返回值就够了，合成库这一步根本没必要，A 的优势来自随机游走和三重验证，不是来自数据库。再预测一个 2×2 格子：{合成库，重放} × {状态变更工具，查询工具}，哪个格子的重放成功率最低并写理由。再构造一个具体反例：一个查询工具的返回值其实依赖于状态——比如“查账户余额”在转账后变了——论文把它归为“查询类、直接重放录好的返回值”，重放时余额还是转账前那个数，断言检查一跑就错；若 A 臂里这类“看似查询、实则依赖状态”的工具不少，三重验证筛掉的样本可能恰恰是最能练“状态跟踪”的那些。漏洞：哪些工具算“状态变更”、哪些算“查询”，分类标准是论文定的还是人工标的，注释和摘要都没说——分类一变，A/B/C 的结论跟着变；而且环境搭建成本没有数字，B 臂“全部合成”到底贵多少没法从注释里核实。
3. Pro 版让 7 个前沿模型掉最多 38.2 分——这个“更难”是真难，还是只是把任务变长了？——综合 Day 03 WorkForge。Day 03 的判断是“真实感是学会探索的原因”，ToolSpace 的 Pro 版（AutomationBench 和 tau3-Bench Banking 的加难版）让前沿模型掉最多 38.2 分，但摘要没说这 38.2 分掉在哪里。设计一个实验：三臂——A 在 Pro 版上按失败类型拆分（工具选错、参数错、顺序错、状态跟踪丢、跨环境衔接断）；B 在原版上做同样的拆分，看 Pro 版的失败分布是不是原版的“拉长版”；C 在 Pro 版上只给模型“更长的上下文/更多的步数预算”，看掉分能不能靠“多给资源”补回来。指标：分失败类型的错误率、平均任务链长度、平均步数。判据：若 A 的失败集中在“跨环境衔接断”和“状态跟踪丢”，而 B 集中在“工具选错” → Pro 版难在“组合与状态”，不是难在“单步工具调用”，ToolSpace 的图方法正好对症；若 A、B 的失败分布形状相同、只是 A 的每类都按比例放大 → Pro 版只是把任务变长、错误累积变多，38.2 分的掉分没有揭示新的能力缺口；若 C 多给步数就能把掉分补回大半 → 掉分的主因是“步数预算不够”，不是“环境更难”，Pro 版的难度标尺本身值得怀疑。再预测一个 2×2 格子：{原版，Pro 版} × {单环境任务，跨环境任务}，哪个格子的掉分最大并写理由。漏洞：“掉最多 38.2 分”说的是 7 个模型里掉得最多的那个，不是平均掉分——平均掉分是多少、哪个模型掉得最少，摘要没给；而且 Pro 版是 ToolSpace 自己造的，用自己造的测试集量自己方法的提升，有“自产自销”的嫌疑——除非 Pro 版的难度经过独立的人工或第三方验证，否则 38.2 这个数字的含金量要打折。

## 核心机制

1. **Motivation**：现有 MCP 环境扩展方法是数据中心式的：先合成一个数据库和场景，再从中推导工具和任务。顺序一错，三个问题跟着来：工具接口可能跟真实接口对不上；工具组合没有真实执行背书，是 LLM 拼出来的；任务很少跨越一个以上环境。长程 agent 真正要练的恰恰是“跨多个真实工具、按依赖顺序走完一长串调用”——数据中心式合成练不到这个。
2. **方法**：工具中心式，把顺序倒过来。先从真实 MCP 服务的执行轨迹和开源 agent 语料里挖依赖：相邻两次调用之间的数据依赖、状态依赖、重试依赖，用确定性规则挖，不用 LLM 判断——这是“执行见证”。挖出来的依赖建成加权工具组合图，聚类成环境。数据库只给会改状态的环境合成；查询类和无状态工具直接重放录好的返回值。然后在图上做状态感知的随机游走：每一步检查状态，不对就回滚；走完一条链，反编译成带断言检查的自然语言任务；最后三重验证 V_state / V_trace / V_out，只保留能从初始状态成功重放的样本。
3. **关键数字**（论文自报，出自 papers.md 注释与论文摘要）：35B 模型（摘要写作 Qwen3.6-35B-A3B）七个长程工具基准均值 23.0 → 41.0（SFT 后）→ 43.2（加 RL）；GLM-5.2 从 44.6 升到 56.6，与 Claude Opus 5 相当；AutomationBench 与 tau3-Bench Banking 的加难 Pro 版上，7 个前沿模型最多掉 38.2 分；消融里执行见证的边胜过 LLM 判定的边，45.8 对 37.8。

加权工具组合图（示意，非论文公式）：

$$w_{ij} = f(\text{调用 } i \text{ 与调用 } j \text{ 在真实轨迹中相邻出现的次数与依赖类型})$$

其中 $w_{ij}$ 是工具 $i$ 到工具 $j$ 的边的权重，依赖类型分三类——数据依赖（ $j$ 的输入来自 $i$ 的输出）、状态依赖（ $j$ 只有在 $i$ 改过的状态下才有意义）、重试依赖（ $i$ 失败后由 $j$ 重试）——边只由执行见证产生，不由 LLM 判断。

三重验证可以写成一个合取（示意，非论文公式）：

$$V = V_{\mathrm{state}} \land V_{\mathrm{trace}} \land V_{\mathrm{out}}$$

其中 $V_{\mathrm{state}}$ 验状态（游走每一步的状态检查与回滚）、 $V_{\mathrm{trace}}$ 验轨迹（调用链本身可执行）、 $V_{\mathrm{out}}$ 验结果（断言检查通过）——三项都过，样本才留下。

## 边界

- 45.8 对 37.8 没有上下文：注释只给了这两个数字，没说是在哪个基准、哪种消融设置下量的——是单基准还是七基准均值、是 SFT 还是 RL 后、LLM 判定边用的是什么模型，一概没说；这个 8 分的差距能不能代表“执行见证”在整个 pipeline 里的贡献，没法从注释里核实。
- “确定性规则”本身是个黑箱：依赖怎么从相邻调用里挖、什么算数据依赖、什么算重试依赖，规则长什么样，注释和摘要都没展开——规则写死了，换一批 MCP 服务、换一种调用风格，规则可能直接失效；规则里有没有人工调的阈值，也不知道。
- 真实轨迹的覆盖面有限：依赖来自“真实 MCP 服务的执行轨迹和开源 agent 语料”——真实轨迹本身就是“已经有人这么用过”的记录，没人走过的组合、新的工具搭配，图里根本没有边；图聚类成的环境再多，也跳不出已有轨迹的覆盖范围，真正的长尾组合还是练不到。
- Pro 版的 38.2 分是自产自销的嫌疑：加难版是 ToolSpace 自己造的，用自己造的测试集去量“前沿模型掉多少分”，难度标尺本身没有独立验证——如果 Pro 版的难法恰好是“ToolSpace 式任务更难”，那 38.2 分量的是“分布外”，不是“能力上限”。
- GLM-5.2 与 Claude Opus 5“相当”没有给对齐口径：56.6 这个数字是七基准均值，但 Claude Opus 5 的分数是多少、是零样本还是同等 SFT 后的，摘要没说——如果 Opus 5 没经过 ToolSpace 数据训练，这个比较是在比“训没训过”，不是比“方法好不好”；而且 43.2（35B + RL）与 56.6（GLM-5.2）之间差了 13.4 分，模型底子不同，方法带来的提升幅度不能直接比。

## 迁移

- “以可执行依赖为合成单元”可搬到任何“多步调用”的数据合成：写代码调 API、做表格调函数、跑实验调工具——只要任务是一串有依赖的调用，合成单元就该是“依赖边”而不是“单个工具”或“单个任务”；关键是先有真实执行轨迹，没有轨迹，依赖边只能靠 LLM 编，编出来的边又回到数据中心式的老路。
- 与 Day 03 WorkForge 构成对照：WorkForge 是“真实工作空间”当环境，ToolSpace 是“真实工具依赖图”当环境。一个强调“空间真实”（16.7K 真实工作空间），一个强调“依赖真实”（执行见证的边）。两者合起来才是完整的真实：空间对了、依赖错了，agent 还是在假环境里练。
- 与 Day 04 ToolLoop 构成对照：ToolLoop 是“分解生成 + 动态自反馈”的闭环，合成的工具调用由 LLM 生成、再由反馈修正；ToolSpace 是“执行轨迹挖依赖 + 三重验证”的闭环，调用关系由执行见证、再由重放验证。一个信任 LLM 的生成能力、靠反馈纠错；一个不信任 LLM 的判断、靠执行背书。Day 04 的结论是“无反馈合成数据比不训还差 2.17 个点”，ToolSpace 的回答是“别让 LLM 编依赖，从执行里挖”。
- 与 Day 05 Data Turnstile 构成对照：Turnstile 把多轮工具交互拆成 DAG、分角色验证，ToolSpace 把工具组合建成加权图、聚类成环境。DAG 和图都是“把调用关系结构化”，但 Turnstile 的 DAG 是为了“分角色验证”，ToolSpace 的图是为了“聚类成环境、随机游走采样”——同一个结构化思路，一个服务验证，一个服务采样。
- 如果复现，第一步先拿一批真实 MCP 执行轨迹，数一数“相邻调用”里有多少是真依赖、多少是巧合相邻：写个简单规则（比如后一个调用的输入里出现了前一个调用的输出字段）跑一遍，人工抽查 100 条边，量一量假边率——如果假边率超过 20%，先修规则再谈建图；再拿 100 条真实轨迹人工标“哪些调用之间真有依赖”，这是后面所有消融的金标准。
