## FSDP 常驻 / 峰值 估算（bf16-mix，32 blocks 近似）

### 单卡不分片（DDP）对照
- 7B：P=7e9，bf16 参数 14GB，fp32 master 28GB，grad 4-14GB，Adam m/v 56GB → 总常驻 ~4P ≈ 56GB fp32 / 28GB+opt
- 13B：bf16 26GB，fp32 52GB，DDP 4P ≈ 104GB fp32 → 单卡 80GB 放不下
- 30B：bf16 60GB，fp32 120GB，DDP 240GB
- 70B：bf16 140GB，fp32 280GB，DDP 560GB

### FSDP 分片后常驻 = 4P/G，峰值 = (P-b)/G + b + (grad+opt)/G

| 模型 | bf16 参数 | G=2 峰值 bf16-mix | G=4 峰值 | G=8 峰值 | 结论 H100 80GB |
|------|-----------|-------------------|----------|----------|---------------|
| 7B   | 14GB | ~42.5GB (已估，2×A100 验证逻辑) | ~22GB | ~12GB | 2× 够，1× 勉强（峰值+CUDA上下文） |
| 13B  | 26GB | ~78GB ( (26-0.8)/2+0.8 + opt片) ≈ 68-75GB | ~38GB | ~20GB | 2× H100 够，4× 更稳 |
| 30B  | 60GB | ~146GB >80GB 放不下 | ~78GB | ~40GB | 4× H100 底线，8× 推荐 |
| 70B  | 140GB | >80GB | ~172GB >80 | ~86GB | 8× H100 临界（需 activation checkpoint），16× 舒适 |

> 注：以上仍是理论，需 H100 `torch.cuda.max_memory_allocated()` 验证，常驻 vs 峰值区分 block 非整模型。
> all-gather 按 block 拼用完即丢，省大头是 optimizer 2× 参数一直分片（Day 3 结论复用）。

### 通信压力预测（H100 NCCL vs CPU gloo 2.6ms 占位符）

- CPU gloo 32 calls all_gather 2.6ms avg 14.5% total（Day 3）→ 不能误读成 NCCL
- H100 预期：
  - 7B G=2：forward all-gather ~18-25% step，backward reduce-scatter ~22-30%，合计 40-55%（overlap 后）
  - 13B G=4：all-gather % 上升到 30-35%（b≈0.8GB/4块，切更细 startup次数炸，需 per-block sweet spot）
  - 70B G=8：通信占比 45-60%，需 overlap + `limit_all_gathers` / `use_orig_params=True`
  - 解决：per-block 仍是 sweet spot（per-layer 太细 latency bound，per-model 太粗峰值回 DDP）

## tokens/sec 补齐方案（待 H100 实测，代码已备）

### 训练侧（FSDP）
```
tokens/sec = (micro_batch * seq_len) / step_time
```
- 7B G=2 H100 预期：micro_batch=2, seq=4096, step≈0.8-1.2s → 6.8k-10k tps / GPU pair，2卡合计 3.4-5k per GPU
- 13B G=4：micro_batch=1, seq=4096, step≈1.4-1.8s → 2.3k-2.9k per GPU
- 70B G=8：micro_batch=1, seq=2048, step≈2.5-3.5s + activation ckpt → 0.6k-0.8k per GPU

> 占位符 1.2k（CPU 理论）→ H100 后应标 *实测*，区分 prefill vs decode，rollout vs train

### rollout 侧（vLLM）
- Agentic RL 长 CoT 500→5000 tokens：prefill 短、decode 长，KV cache 压力是主因
- vLLM 7B：预期 80-120 req/s，输出 500 tok 平均 → tokens/sec 40k-60k (decode bound)
- 长 CoT 5000 tok：吞吐掉到 8-15k tokens/sec，失败率上升（VCJ 超时主导）
- 拆集群原因：train / vLLM rollout 分离调度，避免 rollout 80% wall-clock 卡训练
  - nowcasting 预测 eval 延迟 → 异步 eval（复用 autoscaling burst 预测思路）

### 需要补的分布（H100 跑 rollout 统计）
建议代码：`vllm_rollout_stress_test.py`（已提供），记录：

1. **超时**（长 CoT 5000 tok，推理 wall-clock > SLO 30s）→ 预期 40% of failures
2. **工具调用超时 / 失败**（code exec / sandbox）→ 30%
3. **VCJ / verifier 失败**（verifiable reward 判错）→ 15%
4. **OOM / KV cache evict** → 10%
5. **NCCL / NCCL timeout / preemption** → 5%

总失败率 = fails / total rollouts

- 7B 短 CoT 500 tok：预期总失败率 5-8%
- 7B 长 CoT 5000 tok：预期 12-18%（占位符 12% 在此区间，合理但需标注区间）
- 13B / 70B：模型越大 verifier 越稳，工具链失败占比上升，超长 CoT 失败率 15-25%
